介绍

ROS (Robot Operating System) 是一个开源的机器人软件开发框架, 它不是一个真正的操作系统, 而是一套运行在 Linux 上的中间件, 提供 通信基础设施 (节点之间能通过 topic, service, action 等机制进行消息传递), 硬件抽象 (统一的接口封装各类传感器和执行器) 等, 并且有比较庞大的生态.

ROS1 最初只是为了 PR2 这款机器人设计, 其搭载了工作站级别的计算资源, 由于只需要单个机器人工作, 可以直接有线连接机器人的组件, 也没有很强的实时性需求. 正因如此, 在后续发展壮大走向市场时出现了很多问题.

ROS2 是对 ROS1 的完全重新设计, 旨在解决 ROS1 架构上的根本缺陷. 其在保留了 ROS1 的核心概念 (节点, 话题, 服务等), 但在底层通信, 跨平台, 安全性和实时性等方面做了彻底的重构.

比如 ROS1 是中心化的, 有单点故障, 而 ROS2 是去中心化的 (基于 DDS 的 Discovery 机制); ROS1 只能在 Linux 上运行, 且无法保证实时性, 而 ROS 能够在 Linux/Windows/macOS 上跨平台运行, 且支持实时系统和确定性调度; ROS1 使用 rosbuild 和 catkin 管理项目, 而 ROS2 使用 ament 和 colcon 等等.

相关概念

rosdepc 是国内维护的 rosdep 镜像工具, 其封装了官方的 rosdep, 将软件源替换为了国内的镜像.

  • rosdepc init 会创建 /etc/ros/rosdep/sources.list.d/ 目录, 并写入国内镜像的 rosdep 数据源配置
  • rosdepc update 会根据 /etc/ros/rosdep/sources.list.d/ 下的配置文件下载并缓存依赖映射表到本地 (就像 apt update 一样), 具体放在 ~/.ros/rosdep/ 目录下
  • rosdepc install -i --from-paths src --rosdistro humble --ignore-src -y, 会扫描 src/ 里的 package.xml, 提取出所有 <depend>/<build_depend>, 然后自动调用包管理器安装系统依赖

Package

Package 是 ROS2 中的最小 “可构建, 可分发, 可复用” 单元, 是模块代码的组织形式.

Package 用 package.xml 文件来描述, 需要提供 package name, dependencies, 编译方式, 以及能够提供什么功能.

Node

Node 表示 ROS2 中的一个正在执行的进程, 是通信的基本单元, 负责发布/订阅 topic, 提供服务/调用服务, 执行 Action, 读写参数等.

正因 node 只是一个普通进程, 它可以是不同语言编写, 可分布式运行在不同主机, 在 ROS2 的管理下还有不同的节点名.

Topic

Topic 是 ROS2 中节点之间进行异步, 单向数据通信的一个命名通道, 遵循 publish/subscribe 的模式.

  • Publisher 是向指定 Topic 发送消息的 node
  • Subscriber 是从指定 Topic 接收消息的 node

特点是多对对, 一个 Topic 可以有多个发布者和多个订阅者, 且彼此之间互不感知.

可以简单讲 Topic 理解为一个 “广播通道”, 发布者像电台一样往某个频道发送数据, 订阅者像收音机一样调到该频道接收数据, 双方不需要知道对方的存在.

需要注意, Topic 不是独立进程/实体, 只是定义了消息类型并附带一个名称罢了.

Publisher 内的 DDS 和 Subscriber 内的 DDS 会负责匹配和通信.

Service

Service 是 ROS2 中 node 之间同步, 双向的通信机制, 遵循 Request/Response 的模式. Node 间遵循 Client/Server 模型.

  • Service Server 提供服务, 接收请求并返回响应
  • Service Client 负责向 Server 发出请求并等待响应

每个 Service 也有一个唯一的命名如 /add_two_ints, 用于标识和路由.

Service 是一对一的, 一个 client request 对应一个 server response. 另外也是阻塞的, 客户端发送请求后会等待服务端计算并返回结果.

一个 Service 只会对应一个 Server node.

Parameter

Parameter 是 ROS2 中的一个全局字典, 可以在多个 node 之间共享数据. 其可以进行 node 级别的键值对设置, 用于在运行时读取和修改节点的行为, 无需重新编译或重启.

Action

Action 是 ROS2 中, 用于长时间运行, 可抢占, 可反馈进度的任务的通信机制. 相当于可以完整把握一个任务的进度条, 可以随时暂停.

Action 包含 3 个要素:

  • Goal, 客户端发起的一次任务请求
  • Feedback, 服务端在执行过程中持续汇报的进度信息
  • Result, 任务完成后的最终返回值

比如要求 turtle 旋转 90 度, client 可以持续的到当前旋转的进度, 并且可以打断.

Action 本质上是多个 Service 和 Topic 的组合, 以 /navigate 这个 Action 为例, 底层通信依赖:

  • Service: /navigate/_action/send_goal, 用于提交任务
  • Service: /navigate/_action/cancel_goal, 用于取消任务
  • Service: /navigate/_action/get_result, 用于获取结果
  • Topic: /navigate/_action/feedback, 用于进度反馈（持续推送）
  • Topic: /navigate/_action/status, 用于任务状态变化通知

Distributed Communication

ROS2 是去中心化的, 不同进程, 不同计算机上的节点可以直接通信, 不需要中心节点中转. 这主要依赖 DDS (Data Distribution Service) 提供的节点发现 (Discovery, node 加入网络时会广播自己的 topic, service, action 等信息, DDS 协议会让网络内的 node 相互匹配) 和数据传输能力.

只要在同一网段内能 ping 通, 则能够进行发现. ROS2 用 ROS_DOMAIN_ID 环境变量来分组, 默认是 0:

DDS

常见的通信模型有:

  • 点对点: 每两个节点之间都会有连接, 节点数多时开销很大
  • Broker: 由 Broker 统一处理请求并分发, 依赖单点算力和瓶颈
  • 广播: 同时向所有节点发送消息, 带宽消耗大
  • DDS: 所有节点都可以向一个全局的数据空间写入和读取信息

ROS1 依赖 TCP/UDP 进行数据传输, 而 ROS2 更改为了 DDS (Data Distribution Service).

DDS 是 OMG (Object Management Group) 在 2004 年发布的通信协议, 专门为实时系统的数据分发/订阅而设计.

DDS 只是一种标准, 具体的实现有多种, 为了兼容这些 DDS, ROS2 设计了一个 middleware, 只有适配了该 middleware 接口的 DDS 才能使用:

action

ros2 action 是 ROS2 中的一种通信机制, 区别于 Topic (持续广播, 无确认) 和 Service (请求-响应, 阻塞). 用来处理需要反馈, 可取消的长任务.

比如让 turtlesim 旋转:

  • Service, 发出请求, 阻塞到完成后才返回
  • Topic, 不断发出旋转请求
  • Action, 实时反馈旋转角度, 可中途取消

bag

ros2 bag 是 ROS2 自带的数据记录与回访工具. 可以把系统中流通的 topic, service, action 等消息按时间戳持久化保存到磁盘, 之后能原样复现当时的数据流.

ros2 bag record 会作为一个订阅者节点, 订阅指定的话题, 把收到的消息连同元数据序列化后写入存储文件.

ros2 bag play 则能够读取文件内容, 按照原始的时间间隔重新发布到 ROS2 通信网络中.

Action Server

注意 execute_callback 中只用处理 goal_handle.publish_feedback(xxx) 和 return result. 也就是只用管 topic 的逻辑, service 自动封装好了.

Action Client

流程是这样的:

  • 在 _send_goal_future 这个 request 发出后, server 会不断发布 feedback topic, 而 feedback_callback 会订阅这个 topic, 其注册后一直存在
  • 一次 action request, 会对应一个 action response. self._send_goal_future 的执行表示一次 request, 而这个 future 执行结束则会受到 response, 就用 self.goal_response_callback 来处理
  • 在得到 response 之后, 只是知道了任务是否在执行, 还需要用 get_result_sync() 等待执行结果, 然后用 get_result_callback 处理结果

DDS 配置

DDS 的一大特点是可以精细控制 QoS:

QoS 策略 作用
RELIABILITY RELIABLE（可靠重传） vs BEST_EFFORT（尽力而为，低延迟）
DURABILITY 新订阅者能否收到历史数据（VOLATILE / TRANSIENT_LOCAL）
HISTORY 保留多少条历史数据（KEEP_LAST / KEEP_ALL）
DEADLINE 数据更新最大间隔，超时告警
LIVELINESS 心跳检测，判断节点是否存活
PARTITION 在同一 Topic 内进一步隔离（类似子频道）

TF

TF (Transform) 是 ROS2 中用于管理和追踪多个坐标系之间相对位置和姿态的系统.

在机器人系统中, 通常存在多个坐标系:

  • map 绝对世界坐标系, 视角是不变的
  • odom 里程计坐标系, 会随着里程计漂移
  • base_link 是机器人本体的参考中心

每个传感器的数据都是相对于自己的坐标系, TF 需要负责回答: 激光雷达看到的障碍物, 相对于机器人本体在哪个位置?

坐标系之间的关系变换, 可以用一个矩阵来描述. TF 的本质就是对这部分数学变换的封装.

这里需要注意几个概念:

概念 说明
Frame（坐标系） 一个有名字的坐标系，如 base_link、map
Transform（变换） 两个 Frame 之间的平移 + 旋转（位置和姿态）
TF Tree（坐标树） 所有 Transform 组成的树状结构
tf2_ros 广播器 持续发布 Transform 的节点
tf2_ros 监听器 接收并缓存 Transform，查询任意两坐标系的相对关系

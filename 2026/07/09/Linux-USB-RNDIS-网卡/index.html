介绍

该 Blog 说明一下 USB 协议和 RNDIS 协议 (将 USB 设备视为网卡) 涉及的一些概念, 以及如何在 Linux 上实际创建 USB 网卡.

相关概念

USB

USB (Universal Serial Bus) 是一种串行总线标准, 用于连接计算机和外部设备, 支持数据传输和供电. 1.0 版本在 1996 年由因特尔, 微软, IBM 等多家公司联合敲定. 其设计初衷主要就是为了通用.

在 USB 诞生之前, 键盘鼠标多用 PS/2 接口, 游戏手柄有 Game Port 接口, 打印机等也有串行接口和并行接口, 这些接口规范各不相同, 也有各种缺陷, 比如:

  • PS/2 接口必须在开机前插入. USB 支持热插拔, 即插即用
  • game port 接口的游戏手柄只能支持最多 4 个按键和两个摇杆. 而 USB 接口的当前手柄有各种扳机和拨片

由于 USB 标准传输速度快, 使用方便, 连接灵活, 且无需授权费, 其很快就取代了其他标准. 但其并没有完全实现通用, 为了满足各类硬件的需求, USB 接口也出现了很多中变体:

我们接触到最多的有:

  • 标准 Type-A

  • 标准 Type-B, 通常是打印机的接口

  • Mini-B, 常用于老式 MP3, MP4, 旧手机, 行车记录仪等

  • Micro-B, 大多数数码产品使用

  • Micro-B SuperSpeed, 用在早期的移动硬盘, 少部分手机上

  • Type-C, 近年新出厂的手机, 电脑等都搭载, 部分正反, 使用方便

虽然种类繁杂, 但只需要清楚其大体分为 A, B, C 三种类型, Standard, Mini, Micro 三种尺寸, 且都使用 USB 协议. 苹果使用的 lighting 接口虽然不是标准 USB 接口, 但也使用 USB 协议.

USB 从最初的 1.0 版本到 4.0 版本, 理论最大速度以及从 1.5Mbit/s 到了 40Gbit/s. 需要注意决定 USB 最大传输速度的不是 USB 接口的形态, 而是其支持的 USB 协议版本. 比如就算接口是 Type-C, 但它可能只支持较慢的 USB2.0 协议来传输数据.

USB 接口的引脚定义如下:

  • VCC 是电源线, GND 是地线
  • D+ 和 D- 是差分数据线, 虽然是两根线, 但承载的是同一份数据

原始信号进入后, 会变成两条差分信号线:

  • 在原始信号中, 高电平表示逻辑 1; 低电平表示逻辑 0
  • 而差分信号中, 由两根线的差值表示逻辑 0 或者 1; 比如 D+ 是 3.3V, D- 是 0V, 此时 D+ - D- = 3.3V, 表示逻辑 1; D+ - D- = 0V 时表示逻辑 0

如果只用一根线, 由于 USB 线通常较长, 容易受外部脉冲影响, 导致传输信息出错. 而用两根线时, 即使受到干扰, 也是两根线同时受到干扰, 其差值不会变, 能保证数据的准确性:

USB 采用 NRZI (Non-Return to Zero Inverted) 编码方式:

  • 信号只有在表示 “0” (下降沿) 时发生反转; 在表示 “1” (上升沿) 时保持电平不变 (电平不变时也不变)

USB 主机是轮询制, USB 总线上往往挂载了多个设备, 为了进行区分, 每个设备都会被分配一个唯一地址, 范围是 1~127, 0 是保留的特殊地址, 用来与刚接入的设备通信, 协议规定, 所有刚复位的设备都必须临时使用地址 0 来接收主机的指令. 主机会先请求地址 0 的设备描述符 得到 USB 版本, 厂商ID, 产品ID, 支持的速度, 最大数据包大小等信息. 操作系统就是根据厂商ID, 产品 ID 来安装对应驱动. 之后主机会给设备分配一个唯一的地址, 接收到 device 的 ACK 信号后, 之后请求到配置描述符后就能进行通信了:

USB 有 4 种传输方式:

  1. 控制传输
  2. 中断传输 (比如键盘和鼠标)
  3. 批量传输
  4. 等时传输

需要注意 USB 协议中, 只有 Host 能发起通信, Device 只负责将数据放在总线上. 其设计是非对称的, 总线上的角色并不平等:

  • USB Host, 掌握数据传输的主动权. 负责发起所有传输, 提供 VBUS 电源, 枚举设备, 分配地址等
  • USB Device, 被动响应 Host, 负责消费 VBUS, 报告描述符, 提供数据端点等

USB 的通信单位是 packet (包), 分为 4 种:

  • 令牌包, 用来启动一次数据传输事物
  • 数据包, 用来传输数据
  • 握手包, 用来确认数据是否被接收
  • 特殊包, 特殊场景使用

EndPoint

EndPoint 是 USB 设备内部的一个逻辑端点, 用来表示通信方向, 提供数据收发缓冲区.

每个 EndPoint 有固有的属性:

  • 端点号 (0-15)
  • 方向: IN (device 到 host) 或 OUT (host 到 device)
  • 传输类型: 控制 (Control), 中断 (Interrupt), 批量 (Bulk), 等时 (Isochronous)
  • 最大包大小

(比如 EP1 是 IN, 那么其就不能作为 OUT 传输 host 到 device 的包)

所有 USB 设备必须要有 EndPoint 0, 其是双向的 (Contorol In / Control Out), 用于:

  • 设备枚举
  • 标准请求
  • 厂商特定控制命令

对于 IN EP, 数据从 Device 到 Host, 硬件上会有一个 TX FIFO 缓冲区. 在 Host 发送 IN token 时, Device DMA 引擎会从 TX FIFO 取数据放到总线上.

对于 OUT EP, 数据从 Host 到 Device, 硬件上会有一个 RX FIFO 缓冲区. Host 发送 OUT token 和数据, Device DMA 引起会写入 RX FIFO.

CDC-ECM

CDC-ECM (Communication Device Class - Ethernet Control Model) 是 USB-IF 定义的 CDC 类的一个子类 (Subclass), 作用是让 USB device 在 Host 上模拟成一块标准的以太网卡 (NIC), 通过 USB 传输 IEEE 802.3 以太网帧, 使主机可以通过 TCP/IP 协议栈与 USB 连接对端 Device 通信.

对于 CDC-ECM 设备而言, 其包含两个 Interface:

  • Communication Interface, 用于管理链路状态, 获取 MAC, 设置过滤规则等. 绑定到 EP0 (Control) 和可选的 Interrupt IN EP
  • Data Interface, 负责收发以太网帧. 绑定一个 Bulk IN 和一个 Bulk OUT EP

在实现 CDC-ECM 固件的时候, 就需要让 EP0 来处理控制请求; 用 EP Bulk IN 来发送以太网帧给主机; EP Bulk OUT 来接收主机发来的以太网帧.

RNDIS

RNDIC (Remote Network Driver Interface Specification, 远程网络驱动接口规范) 是微软提出的一种专有协议, 作用跟 CDC-ECM 一样, 让 USB device 在主机上模拟成一块以太网卡, 区别就是它是微软私有的, 不是 USB-IF 标准.

Windows 原生有 RNDIS 的驱动, 即插即用. 而 Linux/macOS 需要 rndis_host 模块, 偶尔有兼容问题.

EHCI/XHCI/DWC2

三者都是 USB Controller, 是 SoC 或主板上负责实现 USB 协议, 驱动总线的硬件:

  • EHCI/xHCI 是 Interl 定义的 PC 主机控制器接口规范 (寄存器级标准)
  • DWC2 是 Synopsys 卖给芯片厂的 USB IP 核, 常见于嵌入式 SoC

EHCI (Enhanced Host Controller Interface) 是 intel 主导制定的 USB 2.0 主机控制器接口规范. xHCI (eXtensible Host Controller Interface) 是制定 USB 3.0/3.x 统一主机控制器规范, 目的是取代 UHCI/OHCI/EHCI.

DWC2 (DesignWare USB 2.0 OTG Controller) 是 Synopsys 公司出品的 USB 2.0 Hi-Speed On-The-Go (OTG) 控制器 IP 核, 卖给芯片厂商集成进 SoC, 其既能做 Host (主机模式), 也能做 Device (设备模式). Linux 驱动通常是 dwc2, dwc3.

前两个是规范, DWC2 是具体硬件.

OTG

OTG (On-The-Go) 是 USB 规范的一个扩展, 用来解决一个问题: 传统 USB, PC 永远是 Host, U 盘永远是 Device. 而 OTG 允许同一个 USB 接口, 根据情况动态决定谁当 Host, 谁当 Device.

比如:

  • 手机插 U 盘, 此时手机是 Host (供电 + 枚举 U 盘)
  • 手机插 PC, 手机当 Device (MTP/CDC/RNDIS)

OTG 有 3 个核心机制:

  1. ID 引脚检测: 对于 Micro-AB 和 Mini-AB 而言, ID 引脚接地 (ID=0) 时, 该设备默认当 Host (A-device); ID 引脚悬空 (ID=1) 时, 该设备默认当 Device (B-device). 对于 Type-C 而言, 不用 ID 引脚, 而是靠 CC 通道 和 Role Detection 来判断
  2. HNP (Host Negotiation Protocol, 主机协商协议), 初始 A-device 是 Host, B-device 是 Device. 当总线空闲时, B-device 可向 A-device 请求换角色, A-device 让出总线后, B 变成 Host, A 变成 Device
  3. SRP (Session Request Protocol, 会话请求协议), 在未供电的总线上, 外设 (B-device) 可发脉冲来唤醒 A-device 开启 VBUS

前面提到的 DWC2 在硬件层面就支持 OTG.

在固件上可以配置 dr_mode = host, dr_mode = peripheral, dr_mode = otg.

Linux 下由 dwc2, usb_gadget 等模块配合实现 OTG 状态机.

VBUS

VBUS (Voltage BUS), 是 USB 接口中那根 +5V 电源引脚, 用来给总线供电, 作为连接检测信号.

UDC

UDC (USB Device Controller, USB 设备控制器), 就是支持 USB 协议的 device 侧的硬件 (比如 DWC2).

设备枚举

USB 设备枚举 (Enumeration) 是指 USB Host 在 device 接入后, 通过一些列标准控制传输 (Control Transfer on EP0), 来读取设备描述符, 分配地址, 选择配置, 使设备从 “未知硬件” 变为 “可用功能” 的过程.

USB device 通过描述符向 Host 报告自己的能力, 这是一个树形结构:

当 USB 线插入时, Host 会做以下事情:

  1. 检测 VBUS/D+/D- 上拉 → 知道有设备插入
  2. Reset 总线 (D+/D- 都拉低 10ms)
  3. 发送 SETUP 包到地址 0, EP0 → GET_DESCRIPTOR(Device)
    设备返回 Device Descriptor (VID/PID/厂商/产品名)
  4. Reset 总线
  5. SET_ADDRESS(新地址) → 设备获得唯一的 7-bit 地址
  6. GET_DESCRIPTOR(Device) again at 新地址
  7. GET_DESCRIPTOR(Configuration) → 设备返回完整配置树
  8. SET_CONFIGURATION(配置号) → Host 选择一个配置
    此后所有端点变为可用
  9. Class-specific 初始化 (如 RNDIS: 控制消息协商 OID)

DDR

DDR 通常指 DDR SDRAM (Double Data Rate Synchronous Dynamic Random Access Memory, 双倍速率同步动态随机存取存储器), 也就是常说的内存/RAM.

  • DDR 在技术上指时钟的上升沿和下降沿都传数据, 同频下带宽是 SDR 的 2 倍 (Single Data Rate, 只在时钟上升沿传输数据)
  • Synchronous, 指与时钟同步工作 (早期是异步 DRAM)
  • Dynamic, 指用电容存储 bit, 需要定期刷新, 断电时数据消失
  • RAM, 随机存取, 可按地址读写

FSBL

FSBL (First Stage Boot Loader, 第一阶段引导加载程序), 是 SoC 上电后, 从 ROM 中加载的第一个程序. 其负责为 SSBL (Secondary Stage Boot Loader, 第二阶段引导加载程序) 比如 U-Boot 准备环境, 比如:

  • 初始化最小 DDR
  • 配置时钟
  • 加载 U-Boot 到 RAM 并跳转执行

SPL

SPL (Secondary Program Loader), 是 U-Boot 项目的一个子模式. 本质上是一个极简版本的 U-Boot, 在完整的 U-Boot 之前运行,做三件事:

  • DDR 初始化
  • 加载 U-Boot proper
  • 跳转

其作用等价于 FSBL, 负责加载和跳转到 U-Boot.

需要 SPL 的主要原因是很多 SoC 的片上 SRAM (Static Random Access Memory, 内容用触发器存储, 不需要刷新, 存储密度低, 速度快) 太小 (通常 32KB-128KB), 装不下完整的 U-Boot (~500KB+). 而 SPL 被精简到只包含硬件初始化代码, 加载完 DDR 和 U-Boot 后就会退出.

GINTSTS 和 GINTMSK

GINTSTS (Global Interrupt Status) 和 GINTMSK (Global Interrupt Mask) 是 DWC2 中一对用来管理中断的寄存器:

  • GINTSTS (0x014) 的每个 bit 指示一种中断事件是否发生. 发生时硬件会自动置位, 需要用软件写 1 来清除 (举个例子, 代码示例)
  • GINTMSK (0x018) 的每个 bit 控制对应时间是否产生中断信号, 写 1 时表示允许中断, 写 0 时表示屏蔽中断

注意这里的 0x014 和 0x018 是一个偏移地址. DWC2 Core Global Registers (全局寄存器组) 是从 USB_OTG_BASE (SoC 映射的物理地址) 开始, 按顺序每 4 个字节一个寄存器来排列的

分层寄存器

分层的意思是, 想要获取一个信息, 往往需要按顺序访问多个寄存器.

DWC2 中, 中断寄存器是分层的, 比如 GINTSTS 寄存器中某个 bit 置位了, 只能说明某个中断发生了, 但细节需要去查别的寄存器, 会先去二级寄存器比如 DAINT 中, 查找比如哪个 EndPoint 发生了什么事, 之后会去第三级寄存器比如 DIEPINTx 中查看这个 EndPoint 具体发生了什么 (传输完成, NAK, 超时等).

分层的原因是 GINTSTS 就只有 32 bit, DWC2 支持 IN EP0 ~ EP15 和 OUT EP0 ~ EP15, 完全放不下.

CORE_SOFT_RESET

CORE_SOFT_RESET 在 DWC2 里叫 CSftRst (Core Soft Reset), 是 USB Controller 内部的一个 “总重启按钮”. 向 GRSTCTL 寄存器的 bit 0 写 1 时, DWC2 核心内部状态机, FIFO, DMA, EndPoint 的逻辑会全部进入复位过程, 这个步骤是硬件异步执行的, 这个期间对所有寄存器的访问都可能出错.

对于复位完成, 需要注意: 对于旧的 DWC2 核心, 当 GRSTCTL 寄存器的 CSftRst (bit 0) 被硬件清 0 时, 表示复位完成.

对于新的 DWC2 核心, Synopsys 发现 “自动清 0” 不可靠, 于是新增了一个显式完成位, 当 GRSTCTL 寄存器的 CSftRstDone 硬件置 1 时表示复位完成.

Shared DFIFO RAM

Shared DFIFO RAM 是 DWC2 内部一块统一的双端口 RAM, 用来做 USB 数据包的临时缓存. 双端口, 意思是这个 RAM 在同一时间允许两个不同的访问操作, 每个 port 有独立的地址线, 数据线, 读写控制信号灯:

这块 RAM 的划分由下面几个寄存器决定:

  • GRXFSIZ (Global RX FIFO Size), RxFIFO 的起始地址固定为 0, 深度由这个寄存器决定
  • GNPTXFSIZ (Global Non-Periodic Transmit FIFO Size), NPTxFIFO 的起始地址自动设为 RxFIFO 末尾, 深度由这个寄存器配置
  • HPTXFSIZ (Host Periodic Transmit FIFO Size), PTXFIFO 起始地址默认是 NPTxFIFO 末尾, 深度由该寄存器配置 (Host 模式)
  • DIEPTXF[n] (Device IN EndPoint Transmit FIFO n Size), 配置各 Device IN EP TX FIFO 的大小, 并依次排列

这里还需要解释一下几个术语:

  • RxFIFO (Receive First-In First-Out buffer), 所有带 USB IN 令牌的数据包都会先进入这里
  • NPTxFIFO (Non-Periodic Transmit FIFO), 在 USB 2.0 中, Control 和 Bulk 事务是 Non-Periodic 的; Interrupt 和 Isochronous 事务是 Periodic 的. 这个 FIFO 就用于存放 Non-Periodic 的要发送的包
  • PTxFIFO (Periodic Transmit FIFO), 该 FIFO 仅在 Host 模式下可用, 用于 Interrupt/Isochronous OUT 发送
  • DIEPTXFx (Device IN Endpoint n Transmit FIFO), 是 Device IN 的端点 EP1 IN ~ EPn IN 各自的独立 TX FIFO

AHB

AHB, AMBA High-performance Bus, 就是一个高速总线.

AMBA, Advanced Microcontroller Bus Architecture, 是 ARM 指定的片上总线标准

DWC2 USB 控制器就是一个挂在 AHB 总线上的 IP 核.

(IP 核, Intellectual Property (知识产权) Core, 指别人设计好, 可以 “拿来就用” 的硬件功能模块.)

AMBA AHB 总线是多 Master, 多 Slave 的结构, 一个硬件既能是 master 也能是 slave, 取决于其内部是否实现了这些接口:

  • AHB Master, 表示能够发起读写事务 (提供地址, 控制信号等) 的硬件, 比如 DWC2 可以作为 AHB Master, 通过 DMA 直接访问内存
  • AHB Slave, 表示能够响应读写事务 (被选中, 返回数据/应答) 的硬件, 同样 DWC2, 其暴露自己的寄存器块供 CPU 读写

也就是说, AHB Master 和 AHB Slave 只是一种角色的分类, 对应不同的功能. 下面是一些例子, 哪些硬件是 Master, 哪些是 Slave:

硬件 AHB Master AHB Slave 说明
CPU 是 否 只发起访问, 别人不能读取
SRAN/ROM 否 是 纯被访问
General DMA 是 是 被 CPU 配置, 也可以主动搬数据
UART/GPIO 否 是 只配寄存器

AHB Master 的状态

AHB 总线规定 Master 有以下几个基本状态 (简化):

  • IDLE, 表示 Master 当前没有发起任何传输请求, 可以开始新的事务
  • BUSY, Master 正在控制总线
  • NONSEQ/SEQ, 正在发起/连续发起读写事务 (比如DMA搬运中)

如果要对 AHB Master 进行配置, 就需要等待其进入 IDLE 状态, 此时对 DFIFO/EP/Reg 的操作才是安全的:

片上

片上, 等价于在芯片内部的意思, 比如:

  • CPU, RAM, USB 控制器在同一个硅片里, 这些内容就都是片上
  • 芯片外接一颗 SPI Flash, 则是片外

SoC, System on Chip, 指一整台 “电脑” 做在一颗芯片里

On-chip memory, 片上存储, SRAM/ROM

On-chip peripheral, 片上外设

DWC2 就是片上 USB 控制器, 它和 CPU 在同一个硅片里, 通过 AHB 总线直连, 不需要外部引脚中转.

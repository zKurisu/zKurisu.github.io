rootfs

因为编译 StarryOS 时, 需要先运行 make rootfs, 因此调研下这个概念.

rootfs 正如其名, Root FileSystem, 是 Linux 内核启动过程中挂载的第一个文件系统, 它是所有其他文件系统的根.

但 rootfs 和寻常我们理解的文件系统有所不同, 它是一个由内核在启动阶段自动创建的存在于内存中的临时文件系统 (类型是 tmpfs), 而非磁盘上. 特点就是它不依赖任何块设备/磁盘驱动, 并且内容为空. 没错, 它是空的.

尽管 rootfs 为空, 但它确实作为了文件系统的根节点了, 其下可以放置文件了.

这里从 Linux 内核启动再理一边. Linux 内核在编译时会链接一个 initramfs (或者是一个独立的 initramfs 文件), 其本质是一个 cpio 压缩包. 内核在启动后, 会进行下面操作:

  1. 创建空的 rootfs (tmpfs)
  2. 把 initramfs 的内容解压到 rootfs 中
  3. 此时 rootfs (/) 之下, 就有了 /init, /bin/, /lib/ 等基本内容

之后内核会执行 /init 文件 (一个 shell 脚本或编译好的二进制), 其会进行:

之后内核会用 switch_root 或 pivot_root (函数), 把根从 initramfs 的 tmpfs 切换到 /mnt/realroot 上.

switch_root 干了 3 件事情:

  1. 把 /mnt/realroot 移动为 /
  2. 清空旧的 initramfs 内容 (释放内存)
  3. 执行新根下的 /sbin/init (系统真正的 init 进程)

之后系统就开始正常运行了.

BootROM

BootROM (Boot Read-Only Memory) 是嵌入式/计算机体系结构中 CPU 上电后执行的第一段代码所在的只读寄存器, 也叫 ROM bootloader 或 Stage 1 Bootloader 这是芯片出厂时就烧死在 ROM 里的代码, 不可修改.

BootROM 负责把真正的 Bootloader 加载到内存并跳转运行, 它是 “引导程序的第0步”, 早于 BIOS/UEFI/SPL/U-Boot.

FIP

FIP (Firmware Image Package), 是一种固件的打包格式 (由 ARM Trusted Firmware 定义), 用于将多个固件镜像打包成一个文件. 比如将 OpenSBI 和 U-Boot 打包成 fip.bin, 作为 Boot Loader Stage 2 来使用.

FIP 的原始概念是: ARM 启动有多个安全级别 (EL3, EL2, EL1 等), 每级需要不同的固件. FIP 将这些固件打成一个包, BootROM 或上一级固件可以从包中提取自己需要的部分. 这里借用了这个术语, 只包含了 OpenSBI 和 U-Boot 两部分.

OpenSBI (Open Source Supervisor Binary Interface), 是 RISC-V 的标准 SBI 固件, 为操作系统提供底层服务 (定时器, IPI, 电源管理等).

U-Boot (Das Universal Bootloader), 是一个开源通用的引导程序, 支持从 SD 卡/NAND/NFS 等加载内核.

从这两个软件的作用也可以看出:

  • OpenSBI (SBI Runtime) 会一直驻留内存 (运行在 M Mode), 内核会持续调用它, 设备树中常用 /reserved-memory 来标记:

  • U-Boot 会在启动完成后退出执行, 通常被覆盖或丢弃

BootROM 解析 FIP 的流程如下:

  1. 读取 fip.bin
  2. 解析 FIP 头
  3. 把 OpenSBI 放到 RAM 的一个保留区域
  4. 把 U-Boot 放到 DRAM 可执行地址
  5. 跳转到 U-Boot
  6. U-Boot 加载内核并跳转

FIT

FIT (Flattened Image Tree), 是 U-Boot 的一种内核打包格式, 将内核镜像, 设备树, ramdisk 等打包到一个二进制文件中. 注意区分前面的 FIP (Firmware Image Package), 其用来打包 Stage 2 Bootloader 和 SBI.

这里又涉及到了几个格式和术语:

  • ITS (Image Tree Source), 是 FIT 镜像的文本描述文件 (类似源文件, 描述包含哪些组件, 如何加载, 加载到哪里等), U-Boot 的 mkimage 工具将其编译为 FIT

  • DTB/FDT (Device Tree Blob/Flattened Device Tree), 一个描述硬件拓扑的数据结构, 由内核在启动时解析

Request Queue

Request Queue (请求队列), 是一种用于缓冲管理请求的数据结构. 通常作为生产者-消费者模式的中间层. 核心思想是:

  • 生产者将请求放入队列
  • 消费者从队列中取出请求并处理
  • 队列充当缓冲区和流量控制机制

/dev/mem 字符设备

/dev/mem 是 Linux 中对内存的文件抽象, 编号为 1:1 (格式是 major:minor, 即 主设备号:次设备号):

  • major 是 1, 表示这是 Linux 内存类字符设备 (memory devices). 告诉内核使用哪个驱动程序
  • minor 是 1, 仅用于区分 major device number 下的不同设备节点. 告诉驱动操作哪一个具体的设备

/dev/mem 的设计目的是: 把物理地址空间当成一个文件. 在 open("/dev/mem") 之后, lseek/read/write 的 offset 就是物理地址, mmap 会把这段物理区间映射到用户态. 其诞生于驱动生态不够完善的年代, 用于 “绕过驱动直接摸硬件”. 它是用户态接口, 存在的意义就是 “没有驱动时先干活”.

在 Linux 上, x86/arm64 默认会开 CONFIG_STRICT_DEVMEM 编译选项, 禁止通过它访问 RAM (只允许 MMIO 区域). 设置内核参数 iomem=relaxed 时可以放宽限制.

内核中的外设驱动在访问物理内存时不会走 /dev/mem 接口, 而是直接用 ioremap 等 API. 用于把一段物理地址映射进内核虚拟地址空间, 属性是 device/uncached.

由于 /dev/mem 直接暴露给用户态脚本而绕过了驱动层, 就必须让内核保证一些性质:

  1. uncached. 如果 /dev/mem 对应的物理内存被映射为 cachable, 那么用户利用 /dev/mem 向 MMIO 进行写操作时, 可能直接停在了 D-Cache 中, 此时设备读取的就是旧副本, 导致操作滞留.
  2. 宽度与对齐. 利用 /dev/mem 来访问 32 位寄存器时, 如果访问长度不对齐, 可能会直接报总线错误, 此时内核可以保证只用 32 位进行操作
  3. 范围. 用户态想操作的物理地址不一定是 “已映射且合法” 的. 如果对未映射或保留区解引用, 用户态会报 SIGBUS, 内核会直接 page fault, 因此内核需要对范围进行校验, 还需要完成 VA 分配, PTE 属性设置和可能的失败处理等

StarryOS 上游有提到为什么没有实现 /dev/mem, 因为他们设计为 “不开放任意物理内存”, 而是为具体设备加 “受控的窄接口”.

启动熵

启动熵是开机早期由固件/平台交给内核的一份种子, 用来给内核 CSPRNG (Cryptographically Secure Pseudo-Random Number Generator, 密码学安全伪随机数生成器) 播种 (seeding, 指把 seed 喂给某个确定性算法). 由确定性算法和秘密种子得到的输出, 能够达成真随机的效果, 就算知道历史输出也推不出下一个.

对于密钥, nonce, 会话 ID, ASLR, TCP ISN, UUID 等都要求不可预测, 即不能用时间戳/地址/计数器这类可重放状态去拼凑得到, 避免攻击者的枚举或重放.

页缓存

Page cache (页缓存) 是内核给 “文件内容” 准备的内存副本, 按页管理. 磁盘 I/O 的粒度也是块/页 (比如 4 KiB), 而文件对用户是字节流, 如果每次 read/write 都直接碰 SD 卡会很慢且造成性能浪费.

页缓存按照 (文件身份, 页号) 进行索引, 作用有 4 个:

  1. 读命中不碰盘 (直接读缓存)
  2. 写先落内存 (延迟写/write-back), 等攒够再批量落盘
  3. 支撑文件映射, mmap 的 PTE 就是指向页缓存里的页帧
  4. 多进程共享一份数据, 同一个文件如果被多次打开也是复用同一缓存对象, 而非多次从磁盘读取

脏页是指页的内容比磁盘上的新 (写进了页, 但还没有写回磁盘). 在淘汰一个脏页前必须先将其写回, 不然会丢失尚未落盘的修改.

Pinned page 是指页被 “缓存之外的人” 持有着 (有人在用这个缓存页), 比如 mmap 做了文件映射, 有 PTE 正指向该页时, pins 字段会加一, 并且教给一个守卫, 在 Drop 时 pins 会减一. 此时不能淘汰该页, 不然持有者会看到悬空/错乱的数据.

LRU

LRU, Least Recently Used (最近最少使用), 是一种淘汰策略: 当空间不够时, 丢掉 “最久没被访问” 的那一个. 这是一种符合直觉的思路, 刚用过的很可能马上再用, 而很久没碰的多半不再碰.

fence.i 指令

程序就是内存里的一堆字节, CPU 的 PC 寄存器负责指向 “下一条要执行的指令的地址 (也可能是相对某个 base address 的偏移)”, 然后反复做五件事:

  • 取指 (fetch), 按 PC 从内存读取指令字节 (也可能命中缓存, 从缓存读取)
  • 译码 (decode), 把指令字节拆开送给 CPU 各个组件
  • 执行 (execute), CPU 按照指令内容执行行为
  • 访存 (memory), CPU 用 load/store 指令对内存进行读写操作
  • 写回 (writeback), CPU 将结果写回内存

对于内存的一个地址, CPU 会有两份备份路径:

  • I-cache, Instruction cache (指令缓存), CPU 读指令时, 会先将其放入 I-cache, 然后再进行后续流程. 如果 PC 又指向了该取指地址, 就能直接从 I-cache 快速取出
  • D-cache, Data cache (数据缓存), CPU 用 load/store 读写的字节先放入 D-cache. 如果后续又 load/store 该地址, 就能直接取出

也就是说, 如果向一个内存地址取过指令, 那么该地址会在 I-cache 中有一个备份; 如果从该地址 load 过数据, 就会在 D-cache 中存在一个备份.

fence.i 主要与 I-cache 相关, 想象一个场景:

  • CPU 执行 store 指令, 向内存 (或者缓存) 的一个地址 A 写入了新的指令
  • CPU 想要 fetch A 地址处的指令, 发现 I-cache 中恰好有条目, 因此直接读取了 I-cache
  • 但是 I-cache 中存放的是老指令

除了 CPU 会读取 I-cache 中老指令这个问题外, 还会有别的情况导致新指令得不到运行: store 指令可能运行在 CPU fetch 之后, 也就是说, 新指令还没写入, CPU 却从地址取出了内容.

因此 fence.i 会做两件事来保证新指令能得到运行:

  1. 调整指令顺序, 让 fence.i 指令之前的 store 都保证运行
  2. 清空 I-cache, 当前 I-cache 失效, CPU 需要重新从其他缓存或内存读取指令

这里要理解 “一致点” 这个概念: 前面提到的 store 不一定是把新指令放到内存, 也可能是 L2 缓存; CPU fetch 也不一定是从内存, 而是从 L2 缓存获取.

  • 存到 L2 缓存, 并从 L2 缓存读取, 那么此时 “一致点” 就是 L2 缓存
  • 存到内存, 并从内存读取, 那么此时 “一致点” 就是内存

fence.i 虽然能保证顺序以及 CPU 能取到最新指令, 但也有坏处: I-cache 需要重新填充, 即需要重新预热.

另外还需要注意, 每一个 hart 都有自己的 I-cache 和 D-cache, 因此一个 hart 执行 fence.i 并不会影响别的 hart. 如果要实现跨核同步, 则需要完成其他一致性的对齐 (这部分暂时不深究).

exec 页

exec 页 不是一个通用的术语, 其想表达的是: execve 系统调用要处理的内存页.

execve 会为新程序创建地址空间并且覆盖掉当前的地址空间, 像 .text, .rodata, .data, .bss 等 section 覆盖的那些虚拟页, 就是 execve 涉及的全部 “页”. 比如 803KB 的 busybox, 只读段就约 175 页.

另一个概念是 “物化 (materialize/populate)”: 意思是为虚拟地址真的分配物理页. 物化一个虚拟地址需要做 4 件事:

  1. 分配物理帧
  2. 放内容, 完成内容拷贝或者清空
  3. 在页表中完成映射
  4. 在虚拟地址所在的 PTE 中填入物理页号

对于一个程序所涉及的页, 并不需要一次性全部 “物化”, 而是 “按需缺页”, 用到哪页时再触发缺页异常去补.

比如 static-PIE 的重定向要写 .got/.data.rel.ro/.bss, 这部分先进行物化, 而剩下的 .rodata 等只读段, 则是按需缺页处理.

按需缺页

按需缺页 (demand paging) 是虚拟内存中最核心的机制之一. 内核先登记某段虚拟地址将来会由什么内容填充, 但是不马上给它物理内存; 等程序真的访问到某页, 且页表中不存在有效映射时, CPU 触发一次缺页异常, 内核这时才分配物理帧, 填内容, 装页表项.

需要有一个认知: 缺页异常并不是 “错误”, 而是设计中的正常流程. 在一次缺页处理完成后, 内核会返回用户态, 重新执行刚才那条指令, 此时就能成功, 而用户态程序自己感觉不到.

这是一种必要的设计: 用户态程序看到的地址空间很大, 且连续, 但物理内存只有 256MiB (一个例子). 如果 mmap 一调用就把物理内存全部用上, 程序连启动都做不到. 因此统一的策略都是 “延迟承诺”: 先记下需要多大, 内容在哪里, 然后在用到时再给.

在一次缺页异常里, 内核会:

  1. 看访问的地址是否落在某个合法区间 (VMA) 内 (不然返回 SIGSEGV)
  2. 检查地址权限 (读/写/执行, 是否越权)
  3. 找这个区间的 “内容来源” (匿名零页/文件的页缓存/COW 私有副本等)
  4. 分配一个物理帧
  5. 把内容弄进去 (清零/从页缓存拷/从 SD 卡读)
  6. 建立对象与索引, 安装页表项
  7. 返回用户态

Pin

Pin (钉住), 指的是把一个物理页帧从 “可以被回收/淘汰” 的集合里摘出来. 意思是一个物理页原本被 LRU (Least Recently Used) 等策略放入了一个 “这个页暂时不会有人用, 可以回收掉释放物理空间” 的集合中, pin 这个操作则可以将其从集合中取出, 不被释放.

Pin 的本质就是增加引用计数, pins += 1 表示 “有人正拿着它”, 而 pins -= 1 表示 “放开了”. 只有 pins == 0 且不脏的页才允许淘汰.

注意 pin 的对象是物理帧, 不是虚拟地址. 因为内核/设备真正依赖的是 “这块物理内存还在, 内容没被别人覆盖”.

Pin 出现的原因就是: 内存随时会因为页缓存淘汰, 地址空间退休, 内存压力回收等机制被清空或重新分配给别的虚拟地址. 如果想持续保留这个物理帧, 就需要额外的字段来标记. 不 pin 住可能会导致:

  • 手里的指针指向的帧已经被回收, 分配给别的进程了, 此时会读到别人的数据, 或者写坏别人的内存
  • 页表项还记录了这个帧, 但它已经被回收了, 此时用户访问到的就是悬空数据 (mmap 语义会直接崩)
  • 设备 DMA 正在往这个帧中写内容, 但帧被回收给了别的用途, 此时会产生静默性错误

COW

COW, Copy-On-Write, 写时复制. 即先共享这部分物理页, 等到真要写的时候才复制. 最经典的例子是 fork.

fork 的语义是把父进程的整个地址空间复制一遍得到子进程. 但现实里, fork 之后绝大多数情况都会立刻 exec, 创建新的地址空间来覆盖掉子进程的地址空间. 因此复制出来的这些页立马就会丢弃掉. COW 就是为这种场景设计的.

COW 的实施分四步:

  1. fork 时, 只复制页表结构, 物理页帧父子共享 (引用计数 +1), 把这些 PTE 改成只读 (写就会触发异常).
  2. 写时: 谁先写哪一页, 就触发写保护缺页异常 (此时就是按需复制)
  3. 判断: 内核会检查 “这一帧还有没有别的持有者”:
    • 如果只有我一个持有者, 直接把 PTE 改成可写, 就地转换, 不需要复制
    • 如果还有别人 (比如父进程, 或者另一个子进程), 则分配新帧, 把 4 KiB 内容复制过去, 装入新的 PTE 并设置为可写
  4. 之后: 父子各自写自己的那一份, 互不影响. 每页只在写时有一次缺页成本

内存原语

内存原语 (memory primitive) 是指内核自己实现的, 最底层的搬运函数, 比如导出成 C 符号的 memcpy/memmove/memset/memcmp. 内核中几乎所有拷贝和清零都会链接到它们, 比如页缓存填充, 页复制, fork 的拷贝, .bss 清零, 缓冲区比较等.

UVC

UVC, USB Video Class, 是 USB-IF 定义的 USB 视频类标准. 摄像头设备输出标准类请求, 标准描述符, 主机侧只需要用一套通用的驱动就能输出流, 厂商不必为每个型号写驱动.

UVC 在 Linux 上表现为标准 /dev/videoN (V4L2), 而 StarryOS 没有 V4L2 子系统, 只能自己编写 CVI ioctl 字符设备 /dev/cvi-usb-camera0.

Motion Coompensation

Motion Compensation (运动补偿), 是视频压缩里的概念. 其本质是重用已有的像素. 比如视频第 1 帧里有一个人在走路, 第 2 帧里他只向右移动了 10 个像素. 如果直接处理, 第 2 帧会重新整张编码, 大量像素其实和第 1 帧几乎一样. 如果做运动补偿, 编译器会只记录参考帧编号, 运动矢量 (往哪移, 移多少), 算残差 (剩下的微小差异). 也就是说复用之前某帧的信息, 减少编码.

MJPEG

MJPEG, Motion JPEG, 是逐帧确立的 JPEG 序列, 即每一帧都是一张完整的 JPEG, 帧与帧之间不做运动补偿 (MJPEG 本身的设计目标只是为了简单, 稳定地逐帧访问 JPEG 序列, 而不是 “最小码率”, 因此不需要做运动补偿).

JPEG, Joint Photographic Experts Group, 本身既是一个委员会的名字, 也指代它制定的静态图像压缩标准. 其目标是在尽量不损失人眼可感知画质的前提下, 把一张图片压到很小.

VPU, JPU

VPU, Video Processing Unit (视频处理单元), 通常在 SoC 中负责 H.264/H.265/VP8/VP9/MPEG 等视频流的硬编码/解码. 驱动通常暴露为 /dev/vpu* 或 v4l2 节点.

JPU, JPEG Processing Unit, 是一种专用硬件模块, 负责 JPEG 静态图/MJPEG 帧序列的硬编解码. 驱动通常暴露为 jpu_enc/jpu_dec 或挂在 V4L2 的 MJPEG 节点下.

这里说明下软解和硬解的区别.

软解指 CPU 负责解码, 通常借助专用的 lib 比如 zune-jpeg/libjpeg, 每个像素都有固定成本. 好处在于灵活性高, 可以处理任何参数和变体, 并且可以观测到错误输出. 缺点就是占用 CPU 运行时间, 效率不高.

硬解指专用硬件负责解码, CPU 只搬运. 好处是专用硬件效率更高, 并且能空出 CPU. 缺点就是只能处理固定参数的输入, 灵活性较差.

MPP

MPP, Media Process Platform (海思) / Multimedia Processing Platform (部分厂商), 其不是一个硬件, 而是绑定软件驱动到硬件模块的框架.

MPP 框架里按照视频数据流顺序排布了一些模块名, 每个模块都代表 “一段职责”, 而非单纯一个芯片:

  • Sensor, 摄像头感光元件, 输出 RAW Bayer 数据
  • VI, Video Input, 视频输入模块, 接 MIPI CSI/BT.1120/LVDS 等物理接口, 收集 Sensor 送来的时序数据, 做简单裁剪并将其绑定到 Pipe (数据采集和通道管理)
  • ISP, Image Signal Processor (图像信号处理器), 是最关键的前端画质模块, 调用 AE, AWB, AF, HDR/WDR 等画面处理技巧, 并将 RAW 转为 YUV 传递给后续流程使用
  • VPSS, Video Process Sub-System (视频处理子系统), 对 YUV 进行缩放 (scale), 裁剪 (crop), 降噪, 锐化, 帧率控制等, 并且分发出多路不同分辨率, 比如:
    • 输出 1080P 到主码流 VENC
    • 输出 640x360 给子码流 VENC
    • 输出 640x640 给算法/AI
  • VENC, Video Encoder (视频编码器), 负责消耗 YUV 帧, 输出 H.264/H.265/MJPEG 码流, 做帧间预测, 运动补偿, 码率控制等
  • VDEC, Video Decoder (视频解码器, 反向链路才用), 消耗 H.264/H.265/MJPEG 等码流, 输出 YUV
  • VO, Video Output (视频输出模块), 把 YUV/解码帧送到显示设备, 管 HDMI/LCD/CVBS 时序

这里还涉及到了一些术语:

  • YUV, 是一种颜色编码方式, Y 表示 Luma (亮度), 黑白信息, 人眼比较敏感; U/V 表示 Chroma (色度), 颜色偏差信息; 由于人对亮度细节敏感, 对色彩位置不敏感, 所以可以通过少存一些 UV 来压缩 (画质看着差不多, 数据量减半), 比如 J:a:b 色度子采样比例:
    • 4:4:4 表示每像素独立 YUV, 无压缩
    • 4:2:2 横向上每 2 个 Y 共用 1 组 UV, 带宽 2/3
    • 4:2:0 2x2 共 4 个 Y 共用 1 组 UV, 带宽只有 RGB 的一半
  • RGB (Red, Green, Blue), 也是一种颜色编码方式, 每个像素存 R/G/B, 适合屏幕显示, OpenCV, 神经网络处理
  • NV12, 指 YUV 4:2:0 的一种内存排布方式
  • NV21, 是 NV12 内存排布中 UV 顺序颠倒过来
  • AE, Auto Exposure (自动曝光), 决定快门时间, 传感器增益, 光圈等, 让画面整体不太暗也不过曝
  • AWB, Auto White Balance (自动白平衡), 决定 R/G/B 增益怎么配, 让白纸在不同光源下看起来还是白的
  • AF, Auto Focus (自动对焦), 内部对焦算法

TLB

TLB, Translation Lookaside Buffer, 是页表的缓存. 现代 CPU 跑程序用的都是虚拟地址, 但内存硬件只认物理地址, 中间需要借助页表和 MMU 完成翻译. 但页表在内存中, 每一次查表很慢, 对于多级页表而言, 一次地址翻译等于多次内存访问. 因此 CPU 在 MMU 里加了一层极小的缓存 TLB, 其缓存了虚拟地址到 PTE (页表项) 的映射关系.

CPU 在访问内存时, 会先看 TLB 里有没有这个虚拟页的映射:

  • 命中 (TLB Hit), 则直接拿物理地址
  • 未命中 (TLB Miss), 此时去内存查页表, 再把结果填进 TLB

通常在页表变更后 (比如释放了部分内存), 就需要让 TLB 中的对应项失效, 避免让 CPU 读到旧的翻译 (riscv64 上是 sfence.vma).

等待锁

等待一个锁空闲有两种方式:

  • 自旋, 反复执行指令读取一个原子变量, 空转烧 CPU
  • 睡眠, 把当前任务挂起, 登记到等待队列中, 让出 CPU, 等持有者唤醒

只要环境支持指令的执行, 就能够自旋等待. 而睡眠则需要调度器, 任务身份, 可保存/恢复的上下文, 调度安全点等.

因此在 interrupt handler 中, 通常只能自旋而不能睡眠: interrupt handler 本身不是调度器管理的执行流 (不是一个可调度的实体), 不会放入运行队列中, 没法挂起和唤醒 (但可以被更高优先级中断).

硬中断 (hard irq) 是指设备 (比如定时器, 串口, 网卡, SD 控制器) 向中断控制器 (这里是 PLIC) 拉一根电信号, CPU 会在当前指令的边界停下正在跑的东西, 跳到内核预先注册的入口去处理. 特点是异步, 随时发生, 由硬件触发, 运行在 S mode, 且会借用被中断线程的栈执行, 进入 trap 时硬件会清掉 SIE, 所以 handler 全程关闭本地中断. 比如串口受到一个字节, SD 卡写完一个块, 网卡收到包等都会触发.

  • softirq, 靠每 CPU 的 pending 位图和 raise_softirq() 来触发
  • ksoftirqd, 交给内核线程, 可以睡眠和等 I/O

(对于 hardirq 和 softirq 都无法睡眠)

IRQ-save 自旋锁

由于 interrupt handler 无法睡眠, 其使用自旋锁就需要考虑一直占用 CPU 导致死锁的问题.

比如一个普通的线程拿到了自旋锁, 正在执行任务, 此时被中断, 如果 interrupt handler 此时也去请求自旋锁, 那么就会忙等. 但是普通线程还没有释放该锁, 所以 interrupt handler 就会一直等待, 此时就宕机了.

因此在普通线程和 interrupt handler 都会访问同一个数据区域时, 需要用 IRQ-save 自旋锁先关闭中断: 此时普通线程会拿到锁, 完成任务, 释放锁, 然后再执行 interrupt handler 的逻辑.

IRQ-save 会清除 SIE 等中断相关内容, 然后再释放时恢复. 虽然中断被关闭, 但是并不会丢失, 硬件和 PLIC 的 pending 位会记住这条中断线, 在 SIE 重新打开时照常投递, 相当于只是推迟了几个周期.

嵌套中断

现在主流的内核都不做嵌套中断, 因为:

  • handler 可被重入后, 所有共享结构都得按照 “可重入” 设计, 死锁面成倍扩大
  • 嵌套深度不可控, 栈溢出的风险上升
  • 当前 handler 的延迟增高, 被高优先级中断插队的次数越多, 正在处理的设备响应越不确定

现在的设计通常是: 同一 CPU 上的 handler 不会被再次中断, 即 handler 执行期间, 当前 hart 不会开始第二个 handler. 这通常靠两层来保证:

  1. 硬件层: RISC-V trap 入口会把 sstatus.SIE 清零 (原值存入 SPIE)
  2. 内核层: handler 分发前用 IrqSaveGuard 保证比关闭本地中断

需要注意其他的 hart 可以并行跑自己的 handler.

可重入

可重入 (reentrant), 是指同一个函数/代码段, 在被 “打断 -> 再次进入 -> 再返回” 的过程中, 结果仍然正确.

中断, 递归, 多线程, 信号处理, 都会涉及到 “被打断后再进入”.

一个函数被称为 “可重入函数 (reentrant function)”, 需要满足: 能够在任意时刻被中断, 且在中断返回前再次进入该函数, 结果不受影响.

可重入函数通常只使用参数, 局部变量和传入的指针所指内容, 不依赖全局变量 (static 变量), 堆上共享且无同步的数据和外部状态 (文件 offset, 硬件寄存器等).

/proc

这里要区分几类文件系统:

  • 磁盘文件系统, 比如 ext4, 内存存放在硬盘, 持久化存储 (重启后仍然在)
  • 内存文件系统, 比如 /tmp, /dev/shm, RAM 里真实存在的数据, 非持久化 (重启后消失)

对齐要求

在操作地址时, 通常有 “对齐的要求”. 这是硬件层面的限制, 根据访问宽度不同, 对齐的要求也不同:

  • 用 lb/sb (load byte/store byte) 指令时, 每次只访问一个字节, 永远合法
  • 用 ld/sd (load double/store double) 指令时, 要求地址时 8 的倍数

当地址不对齐时, 硬件有两条路:

  • 直接 trap, 把这件事交给软件的未对齐处理程序
  • 内部拆成两次总线访问, 然后把结果拼起来. 这里要解释一下: 比如我们访问的是地址 1, 如果要读 8 字节, 则是 1~8 这几个地址的内容. 在访问宽度是 8 字节时, 内存地址都是 8 字节的块, 比如 0~7 是一个块, 8~15 是一个块. 如果访问地址时 8 的倍数, 也就是对齐, 那么此次访问直接取一个块. 但这里 1 不是 8 的倍数, 那么其访问就会跨两个块, 因此这里会分别访问两个块然后将结果合起来
    (这些方式都会让程序更慢)

不同的访问宽度需要不同的地址对齐:

  • u8, 1 字节对齐, 访问永远合法
  • u16, 2 字节对齐, 要求访问地址 % 2 == 0
  • u32, 4 字节对齐, 需要 % 4 == 0
  • u64, 8 字节对齐, 需要 % 8 == 0

对齐可以更大, 但不能更小. 比如 u16 访问可以 4 字节对齐, 8 字节对齐, 但是不能 1 字节对齐.

iomap

iomap, I/O memory map, 用于将一段物理地址 (寄存器窗口, 跨核共享 RAM 等) 映射成内核可访问的虚拟地址. Linux 里对应的是 ioremap() 家族.

内核在启动之后, 可以操控一片线性映射的物理地址, 但并不包括 MMIO 地址和固件保留区. 因此需要 iomap 来完成映射.

这里需要对比一下 mmap:

  • iomap 由内核代码发起, 映射到内核地址空间, 还可以设置 DEVICE, UNCACHED, CACHED 等属性. 生命周期随驱动 (与进程无关), 只有内核能访问
  • mmap 由用户进程发起, 映射到调用者进程的用户地址空间, 属性由驱动决定. 生命周期随进程的 VMA (virtual memory area), 该进程可以访问

First touch

First touch (首触), 是指某个虚拟页第一次被访问 (读或写都算). 此时由于按需缺页 (一个页在第一次被访问之前, 既没有物理帧, 也没有页表项), 会触发缺页异常, 让内核分配帧, 填充内容, 建立页对象和索引, 装 PTE 等. 之后的访问就能 “命中”, 只剩 MMU 翻译开销.

因此可以用 first touch 来计算缺页的开销.

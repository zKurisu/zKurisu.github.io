PascalCase

UE 把 PascalCase (大驼峰命名) 用到了类型, 函数, 成员变量, 局部变量和参数等几乎所有地方.

C++ 本身并没有规定变量或函数必须小写开头, 这里的风格是 Epic 制定的一套项目编码规范. Google 的 C++ 规范也要求普通函数采用 CreateSession() 这样的大驼峰, 变量则采用 player_health 这种 snake case 风格.

常见的几种命名形式有:

  • 小驼峰 camelCase, 如 playerHealth
  • 大驼峰 PascalCase, 如 PlayerHealth
  • 蛇形 snake_case, 如 player_health
  • 全大写, 如 MAX_PLAYERS

UE 的代码主要采用 PascalCase, 宏采用全大写.

但 UE 并不是所有标识符都以大写字母开头, 比如 bIsConnected 的 b 就是小写. 标准库接口, 第三方库以及部分特殊接口, 也有自己的命名.

Pawn

Pawn 是 UE 中可以被 Controller 接管和控制的游戏实体的基类, C++ 类型叫 APawn. 玩家操控的人物, 汽车, 飞机, 无人机等, 都可以用 Pawn 或它的子类表示.

其在继承链中的位置是:

  • AActor 作为实体存在于游戏世界中
  • APawn 在 Actor 的基础上, 加入了与 Controller 配合的控制机制
  • ACharacter 在 Pawn 的基础上, 提供胶囊体, 骨骼网络和角色移动技能

Pawn 表示 “被控制的实体”, Controller 表示 “如何控制它”.

Controller 接管 Pawn 的过程叫 Process, 解除控制较 UnProcess.

常用的 API 有:

  • PlayerController->GetPawn(), 获取这个控制器正在控制的 Pawn
  • Pawn->GetController(), 获取正在控制这个 Pawn 的 Controller
  • PlayerController->Process(Pawn), 接管这个 Pawn
  • PlayerController->UnProcess(), 解除当前控制

在多人游戏中, 正式的接管操作通常由服务器执行.

Pawn 本身不保证已经具备走路, 跳跃或可见模型. ACharacter 适合常见的人物运动, APawn 给其他控制形式提供了更灵活的空间.

UGameInstance

GameInstance 负责与 “这次游戏运行” 相关的管理, 常用于保存跨地图的数据, 组织登录和会话流程. 服务器和客户端各自有自己的 GameInstance, 客户端修改其中一个变量, 服务器的对应变量不会自动改变.

前缀命名约定

一些前缀命名能便于开发者从名字判断它大概属于什么类型. 对于参与 UE reflection 的类型, UHT 还会检查许多命名规则.

常见前缀有:

前缀 通常表示 例子
U UObject 体系中的类 UWorld, UCameraComponent
A Actor 及其派生类 AActor, ACharacter
F 大多是其他类, 结构体或具体类型 FString, FVector, FHitResult
T 模板类型 (Template) TArray, TMap, TObjectPtr
E 枚举类型 ETravelType, ECollisionChannel
I 接口 IInteractable, IOnlineSubsystem
S Slate 界面控件类型 SWidget, SButton
b 布尔变量 bReplicates, BIsDead
G 常见的全局变量命名惯例 GEngine, GWorld
In, Out 参数的数据流向 InName, OutHit

但要注意, 这些前缀对应的类, 函数, 的能力都来自继承关系和引擎实现. 仅仅给普通 C++ 类起一个 U 开头的名字, 不会让它自动获得这些能力.

历史上, F 源于 Float, 早期 FVector 等数学类型使用浮点数, 这种命名随后扩展到其他类型, 逐渐成为惯例.

Actor

Actor 是 UE 游戏世界中, 一个可以独立存在, 被创建和管理的 “游戏实体”. C++ 中对应的基类是 AActor. 比如人物, 武器, 门, 灯光, 摄像机, 触发区域等都可以是 Actor.

AActor 所在的继承链是:

  • UObject 是 UE 对象系统的基础, 支持反射, 对象管理等
  • AActor 是参与世界和关卡生命周期的游戏实体
  • APawn 是可以被 Controller 控制的 Actor
  • ACharacter 为角色移动准备好的 Pawn, 带胶囊体, 骨骼网络和角色移动组建

Actor 提供几个入口函数:

  • BeginPlay(), 在 Actor 开始参与游戏时运行, 负责初始化
  • Tick(DeltaTime), 周期性运行
  • EndPlay(...), 在运行结束时负责清理

运行时通常用 World->SpawnActor(...) 创建 Actor, 通过 Destroy() 销毁.

UE5 reflection

Reflection (反射) 通常指: 程序能够检查自身的结构, 并根据这些信息执行操作. 比如在运行时完成:

  • 查询一个对象属于什么类型
  • 查看这个类型有哪些字段, 方法
  • 根据一个字符串形式的方法名, 找到并调用对应的方法

UE5 Cpp 提供了一系列标记宏, 能在声明时给变量/对象等附加信息. UE5 能通过 reflection 检查出标记内容, 进而完成一些任务.

比如:

  • float Damage = 20.0f; 是普通的 C++ 声明和赋值
  • UPROPERTY(...) 是 UE 提供的宏, 用于标记属性
  • EditAnywhere, BlueprintReadWrite 是说明符, 配置属性的行为
  • Category = "Combat" 指定它在编辑器中的分类

UE 的 Unreal Header Tool (UHT) 会读取这些标记并生成引擎需要的代码, 之后再交给普通 C++ 编译器编译.

常见的标记有:

  • UCLASS(...), 声明参与 UE 对象系统的类
  • UPROPERTY(...), 标记成员变量, 使其成为 UE 属性
  • UFUNCTION(...), 标记成员函数, 使其成为 UE 可识别的函数
  • USTRUCT(...), 声明可被反射系统识别的结构体
  • UENUM(...), 声明可悲反射系统识别的枚举
  • UINTERFACE(...), 声明 UE 接口的反射部分
  • GENERATED_BODY(), 在类或结构体内部接入 UHT 生成的代码
  • UMETA(...), 为枚举项等添加元数据

注意并不是所有变量和函数都需要被标记. 比如有些仅用于计算的辅助函数.

UCLASS 中使用的说明符控制该类如何被 UE 使用:

  • Blueprintable, 允许以这个 C++ 类为父类创建蓝图
  • BlueprintType, 允许在蓝图中使用这个类作为变量类型
  • Abstract, 声明 UE 层面的抽象基类
  • Config = Game, 指定该类的配置属性使用 Game 配置体系

UPROPERTY 使用的说明符用来区分编辑权限, 蓝图访问权限和 C++ 访问权限:

  • EditAnywhere, 类默认值和关卡中的对象实例都可编辑
  • EditDefaultsOnlu, 类默认值可编辑, 但关卡中的对象实例不可编辑
  • EditInstanceOnly, 类默认值不可编辑, 关卡中的对象实例可编辑
  • VisibleAnywhere, 类默认值和关卡中的对象实例可查看
  • VisibleDefaultsOnly, 类默认值可查看, 关卡中的对象实例不可查看
  • VisibleInstanceOnly, 类默认值不可查看, 关卡中的对象实例可查看
  • BlueprintReadOnly, 在蓝图中可以读取, 但不能赋值
  • BlueprintReadWrite, 在蓝图中可读可写

Multiplayer games

这里的 Multiplayer games 特指联网多人游戏, 游戏运行在多个终端上, 通过 internet 交换信息, 而非本地多人游戏 (比如连接两个手柄一起玩).

这类游戏的基础问题就是数据同步, 比如有两个 player, player 1 的移动要让 player 2 感知到; 反之 player 2 的移动也要让 player 1 知道:

一种信息交换的方式是 Peer to Peer, 即两个主机直接通信:

好处是实现容易, 但坏处就是 player 变多时信息浪费较大.

另一种更好的方式是 client-server model, 由一个 server 统一收集所有 client 的信息并分发同步:

这又有两种实现方式:

  1. Listen Server: 一名玩家同时当 “玩家” 和 “服务器”. 比如你创建房间, 邀请朋友加入, 此时你的游戏实例同时承担两个角色:

    • 客户端角色: 显示画面, 接收你的键盘, 鼠标输入
    • 服务器角色: 管理整个对局, 处理所有玩家的操作, 判定并同步结果

  2. Dedicated Server: 独立运行一个专门的服务器实例. 服务器只负责对局逻辑, 通常不渲染游戏画面, 也没有他自己操作的玩家, 所有玩家通过客户端加入.

这里还有一个概念: Authoritative client-server, 意思是服务器维护权威的游戏状态, 客户端维护它的近似副本; 发生分歧时, 以服务器的结果为准 (这里的 authoritative 指服务器拥有最终裁决权).

例如, 按照服务器判定射击的设计, 玩家 A 向 B 开枪:

  1. A 的客户端发送请求：“我在这个方向开火了。”在 UE 中，可以通过 Server RPC 请求服务器执行对应逻辑。
  2. 服务器处理并判定：检查弹药、射击间隔、是否命中，然后计算伤害。假设 B 的生命值从 100 降为 80。
  3. 服务器同步结果：通过 Replication（复制/同步），把 B 的新生命值发送给需要知道它的客户端。
  4. 客户端更新表现：显示血条、受击动画等。

如果 A 只把自己客户端里的 B 的生命值改成 0, 服务器上的 B 并不会因此死亡.

Online Subsystem

UE5 的 Online Subsystem (OSS), 是一套访问在线服务的统一接口. 其主要帮助游戏处理账号登录, 创建和搜索房间, 好友邀请, 成就, 排行榜等功能, 具体平台的能力由 Steam, Epic Online Services 等实现提供.

毕竟玩家自己的电脑通常只有 local ip address, 如果创建了一个房间, 用之前硬编码的方式, 别的局域网的玩家就无法连接. 接入 OSS 之后就能避免这个问题.

Creating our own subsystem

这里要考虑, 用于实现插件功能的 class, 应该继承哪个类才更方便. 一个选项是 GameInstance, 因为其在游戏创建时一同创建, 并且在游戏停止时才会销毁, 在 levels 之间转换时也不会消失.

但是项目设置中 Game Instance Class 只能选择一种类, 如果插件继承自 GameInstance, 意味着使用该插件就得把原来的 GameInstance 指向这个类. 如果别的插件也是继承 GameInstance 类, 则会更麻烦. 因此更好的方式是继承 UGameInstanceSubsystem, 其与 GameInstance 的关联在于, 以下面为例:

  • 在 UGameInstance 创建之后, 也会创建一个 UMyGamesSubsystem 的实例
  • 当 UGameInstance 初始化之后, 会调用 subsystem 的 Initialize()
  • 当 UGameInstance 销毁后, 会调用 subsystem 的 Deinitialize()
  • 当 subsystem 的 reference 被 drop 之后, GC 会回收它

Rust-process-macro

介绍

Process macro (过程宏), 指用 Rust 扩展一段 Rust. 语法是 #[xxx], 其主要分三类:

  • Derive macro, 用于给类型 “自动增加实现”
  • Attribute macro, 定义处理函数接收 Item 和属性参数, 返回新的 Item
  • Function-like macro, 定义一个函数, 但可以用宏的方式调用

一些 attribute 与 Rust 编译器自身紧密相关, 除此之外还有很多可以通过 proc_macro crate (编译器提供) 配合 quote 和 syn crate (社区第三方) 来自己实现.

编译器内置 attribute macro

proc_macro 只能生成新的 Rust 代码, 但不能控制符号 mangling, 链接策略, 编译器指令生成等等. 因此像 #[no_main], #[no_std] 这类, 其实不能叫做是 attribute macro, 它们是编译器直接识别的 attribute, 不能用 proc_macro 来复现实现.

下面说明一些编译器内置的 attribute 的使用:

#[repr]

#[repr] (representation), 指内存中的表示. 他告诉编译器: “这个类型在内存中该长什么样”. 核心是对齐 (alignment) 和填充 (padding).

由于 Rust 默认不保证字段顺序和内存布局, 因此编译器会自己做一些优化, 而加上 #[repr(...)] 则是告诉编译器: “别优化, 按我指定的排列”.

#[repr(C)]

#[repr(C)] 表示按照 C 编译器的方式来排列. C 的规则是:

  1. 保证源码声明顺序
  2. 每个字段的 offset (起始地址) 必须是对齐值 (align, 可以用 align_of 函数来得知, 基本就是类型对应的字节数) 的整数倍 (offset % align == 0)
  3. 整个 struct 的大小必须是最大对齐值 (所有字段的对齐值中最大的那个) 的整数倍

在通过 FFI 传给 C 代码时, 必须启用这个.

#[no_mangle]

需要先了解什么是 “Name Mangling”.

代码编译后的二进制文件里, 每个函数会对应一个符号 (symbol). 链接器靠符号名来找函数.

C 对于函数的处理是 “函数名即符号名”, 这很简单, 但遇到同名函数就会出问题. 为此, Rust 会根据模块路径, 泛型参数, 版本 Hash 等信息来对函数名进行编码, 从而得到一个唯一的全局符号名.

必须使用 #[no_mangle] 的场景

主要有 3 种:

  • Rust 函数会被 C 调用
  • Rust 函数会被汇编或 linker script 调用
  • 利用函数名动态查找符号

不能使用 #[no_mangle] 的情况

  1. 不能对泛型函数使用, 因为用不同类型调用泛型函数, 会让编译器为其生成多个符号名, 但应用了 #[no_mangle] 后生成的符号名相同, 此时会出错
  1. 不能用于关联函数/方法

通常会在 #[unsafe(naked)] 里搭配 naked_asm!, 其与 asm! 的区别在于, asm! 会假设编译器把栈帧管理好了 (就是 prologue 和 epilogue 部分), 因此对寄存器进行读写后, 也能在栈帧弹出时恢复. 同时也能进行变量映射.

而 naked_asm! 假设 sp 为初始化, ra 是随机值, 没有栈帧:

  • 不能用 in/out 这些变量映射, 此时编译器也无法知道
  • 不能 ret, 栈上没有返回地址
  • 只能跳转到别的地方, 用 tail 或 j, 又或者 wfi 死循环

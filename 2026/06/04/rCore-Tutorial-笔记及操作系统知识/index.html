操作系统对硬件的抽象示例:

将 I/O 设备抽象为文件, 将内存抽象为地址空间, 将处理器资源抽象为进程. 同时文件也是以地址空间形式组织, 进程也包含地址空间和文件作为其组成.

  • 内存管理
  • 进程管理
  • 处理器调度
  • 同步互斥
  • 文件系统
  • I/O 子系统

操作系统起承上启下的作用, 向上为应用开发提供便利 (比如提供 syscall), 向下管理硬件 (比如 CPU 分配, 内存, 硬盘等管理, 也能够更好支持应用开发).

对于寻常提到的 “操作系统”, 比如 Windows, Linux, 安卓, 这些通常是包含了 “应用程序” 这一层. 这里要学习的 “操作系统” 用更精细的范围来讲是 “OS kernel”.

操作系统的一个核心就是 “支持应用”. 如果一个软件不是为了支持应用, 那么它肯定不是 OS.

操作系统通常会对物力资源进行抽象 (也可以说是一种虚拟化), 比如:

物理资源 操作系统抽象 关键概念
CPU 进程/线程 调度、上下文切换
内存 虚拟地址空间 分页、分段、交换
磁盘 文件 文件系统、inode
网络/外设 Socket/设备文件 驱动、中断处理

操作系统内核通常有下面特征:

  • 并发: 计算机系统中同时存在多个运行程序
  • 共享: 程序间 “同时” 访问互斥共享各种资源
  • 虚拟: 每个程序 “独占” 一个完整的计算机
  • 异步: 服务的完成时间不确定, 也可能失败 (这里的异步可能和后面的异步含义不同)

操作系统历史的演变

还有什么典型系统没有提到? 下面系统的特点是什么? 操作系统的组成是什么? 相比于之前有什么改进? 有什么问题?

  • 单用户系统 (LibOS), 一台计算机同一时间只能被一个用户使用, 此时用户独占全部硬件资源 (CPU, 内存, 外设). 由于操作系统的功能极简, 本质上就是一组程序库, 因此也称 Library OS

此时没有 “内核” 的概念, 也没有保护机制, 程序可以直接访问任意内存空间.

  • 批处理系统, 核心思想是将多个作业 (Job) 收集成一批, 由常驻内存的监控程序自动依次执行. 程序员不再直接操作机器, 而是将程序交给操作员. 相比 LibOS 而言, 能减少一些人工干预, 一批任务能自动顺序执行. 但当前面的任务在等待 I/O 处理时, CPU 也不会空出来给后续任务使用
  • 多道程序系统, 核心思想是内存中同时驻留多道作业, 当一道作业等待 I/O 时, CPU 立即切换到另一道作业. 此时的目标是最大化 CPU 利用率

需要硬件支持中断系统, I/O 完成后硬件通知 CPU. 也需要 DMA 支持, 外设直接和内存交换数据, 无需 CPU 参与. 多个作业在内存中需要隔离, 同时 CPU 要有调度程序决定哪个作业获得 CPU.

  • 分时系统, 核心思想是CPU 时间被切分成极短的时间片 (time slice), 轮流转分配给多个联机终端用户. 及时性强, 能让多个用户同时使用一台主机, 且每个用户相互独立

操作系统结构

单体分层结构: 将单体操作系统 (Monolithic OS) 划分为多层 (levels), 每层仅依赖于相邻底层的接口, 比如最底层 (layer 0) 是硬件驱动, 最高层 (layer N) 是用户界面:

这会产生一个问题, 有时候我可能需要跨层的功能, 需要绕过一些中间层, 此时就很不方便.

微内核结构: 尽可能把内核功能移到用户空间, 用户模块间的通信仅通过消息来传递.

  • LPC (Local Procedure Call)
  • HAL (Hardware Abstraction Layer)

好处在于内核精简比较灵活和安全, 但坏处就是频繁的通信会带来很大的性能开销. 在部分安全要求高的场景下可能会使用.

外核结构: 程序直接链接到操作系统库, 只有与硬件交互的内容存在于外核中, 外核虚拟出多个外设来处理这些请求.

这种方式可以为应用定制操作系统库, 也能更好利用外核提供的服务.

虚拟机结构: 虚拟机管理器将单独的机器接口转换成很多的虚拟机, 每个虚拟机都是一个原始计算机系统的有效副本, 并能完成所有的处理器指令.

Compiler 与 OS

Compiler 负责把程序转换为特定硬件的执行码. 而 OS 负责把这段执行码跑起来.

通常我们在 x86 的机器上开发, 但目标硬件环境是 RISC-V. 因此需要熟悉交叉编译的环境.

整个流程通常是 bootloader 加载 OS 并执行, 之后程序代码经过编译器/汇编器/链接器, 从源码变为汇编指令, 再变为机器码, 最终由 OS 来加载执行.

对于编译器, 需要了解一个三元组 (CPU架构/厂商/操作系统) 来描述目标架构信息:

  • none-elf 表示不依赖特定操作系统, 可以在裸机上运行

最终会得到 ELF 文件 (Executable and Linkable Format, 包含可执行机器码和描述信息).

在编写代码时, 有两种库需要注意:

  • 标准库: 通常以来操作系统, 比如 Rust 的 std 标准库, C 的 glibc
  • 核心库: 与操作系统无关, 比如 Rust 的 core 库, C 的 Linux kernel libc (与 kernel 绑定)

OS 内存布局

编译器不会对 heap 部分做管理, 因为这部分变量的大小无法判断.

bss (Block Started by Symbol) 段属于静态内存分配, 通常是指用来存放程序中未初始化的全局变量的一块内存区域. 但在 Rust 中不允许出现未初始化的全局变量, 不然就是 unsafe 的.

data 段用来存放初始化了的全局变量.

text 段是代码段 (code segment/text segment) 是指存放执行代码的内存区域, 这部分区域的大小确定, 通常属于只读. 在代码段中, 也有可能包含一些只读的常数变量.

heap 是用于动态分配的内存段, 可以动态扩张或缩减. 程序调用 malloc 等函数时, 新分配的内存会被动态添加到堆上. 之后调用 free 等函数时, 释放的内存会在堆中被删除.

stack (栈), 是用户存放程序临时创建的局部变量. 函数被调用时, 其参数和函数的返回值也会放到栈中. 由于栈的先进后出特点, 其能够方便地用于保存/恢复当前执行状态. 放在栈上的变量一定是在编译期已知大小的.

可以把 stack 看作一个寄存, 交换临时数据的内存区.

函数调用本质:

函数调用约定 (Calling Convention), 其规定在某个指令集架构上, 某种编程语言的函数调用如何实现, 其包括下面内容:

RISC-V 的函数调用规范如下:

寄存器组 保存者 功能
a0~a7 (x10~x17) 调用者保存 (caller) 用来传递输入参数, 其中的 a0 和 a1 还用来保存返回值

隔离机制

隔离机制通常需要解决这些问题:

  • 防止程序 X 破坏或监视程序 Y
  • 防止进程干扰操作系统
  • 防止恶意程序, 病毒, 木马和 bug

在操作系统语义下, 隔离可以定义为: 操作系统中的应用程序不会影响 (或破坏) 其他应用或操作系统的正常执行或信息泄露.

隔离的本质是在需要交换信息或共享资源的情况下才出现, 隔离并不意味着不要共享.

隔离需要建立边界 (boundary). 便捷决定了各自的势力范围, 当跨界出现时 (即共享资源) 会有风险. 运行的程序通常是一种隔离单元.

隔离的方法通常有: 基于软件的隔离, 基于硬件的隔离, 基于网络的隔离. 这里特别注意的是利用处理器进行硬件的隔离.

OS 对 Application 的隔离可以分为下面几类:

  • 对控制的隔离: 特权级机制, 如用户态和内核态
  • 对数据的隔离: 地址空间, 如用户地址空间和内核地址空间
  • 对时间的隔离: 中断处理, 随时打断正在执行的用户态 application
  • 对破坏隔离的处理 (不按照隔离方式进行时的处理手段): 异常处理

特权模式的隔离机制

特权通常指: 能够对计算机系统进行管控的操作.

CPU 硬件中的特权模式可以: 防止应用程序访问设备和敏感的 CPU 寄存器 (比如地址空间配置寄存器, 关机相关的指令或寄存器).

CPU 硬件通常要支持两个特权模式: Kernel Mode (内核态) 和 User Mode (用户态).

Kernel Mode 可以执行 User Mode 无法执行的特权操作, 比如访问外设, 配置地址空间 (虚拟内存), 读/写特殊系统级寄存器等.

OS Kernel 运行在 Kernel Mode, 而应用程序运行在 User Mode.

每个重要的微处理器都有类似的用户/内核模式区分.

中断/异常机制

处理器要支持中断/异常的处理, 才能够及时响应和处理应用的异常行为. 比如要打断一直占用 CPU 的应用程序.

中断是异步发生的, 通常来自处理器外部的 I/O 设备的信号.

硬件中断不是由任何一条专门的 CPU 指令造成的, 从这个意义上它是异步的.

硬件中断/异常的处理程序通常称为中断处理程序 (Interrupt handle), 一个示例流程如:

  1. I/O 设备通过向处理器芯片的一个引脚发信号, 并将异常号放到系统总线上, 以触发中断
  2. 在当前指令执行完后, 处理器从系统总线读取异常号, 保存现场, 切换到 Kernel Mode
  3. 调用中断处理程序, 当中断处理程序完成后, 它将控制返回给下一条本来要执行的指令

可以用 Timer 来稳定定时地产生中断, 防止应用程序死占着 CPU 不放, 让 OS kernel 能周期性地进行资源管理.

RISC-V 系统模式

这里涉及下面术语:

  • 应用程序二进制接口 (Application Binary Interface, ABI)
  • 应用执行环境 (Application Execution Environment, AEE)
  • 管理员二进制接口 (Supervisor Binary Interface, SBI)
  • 管理员执行环境 (Supervisor Execution Environment, SEE)
  • Hypervisor: 虚拟机管理程序
  • Hypervisor 二进制接口 (Hypervisor Binary Interface, HBI)
  • Hypervisor 执行环境 (Hypervisor Execution Environment, HEE)

注意都是先构建好 Execution Environment, 然后暴露出 Binary Interface.

RISC-V 对应的架构图如下:

这里是不同 RISC-V 架构的实现, 最左边的只有 M 和 U mode, 中间的有 M, S, U mode, 右边的有 M, H, S, U mode. 可以根据具体应用来组合. 比如:

  • M Mode: 蓝牙耳机
  • U+M Mode: 电视遥控器
  • U+S+M Mode: Android 手机
  • U+S+H+M Mode: 数据中心服务器

这里主要讲中间这种.

RISC-V 定义了三种主要的特权级别, 加上一个可选的 Hypervisor 扩展的话就是 4 种:

  • M-Mode (Machine mode), 所有 RISC-V 实现都必须有, 对应固件/bootloader 等程序运行的环境
  • H-Mode (Hypervisor mode), 可选, 对应虚拟机管理器 (VMM)
  • S-mode (Supervisor mode), 传统的 OS 需要, 对应 OS 内核
  • U-mode (User mode), 可选, 对应普通程序和应用

每多一个 Mode, 都是为了增加一层隔离, 防止上层低权限应用对下层造成破坏. 越多的 Mode 灵活性更高, 但复杂性也会相应提升.

U-Mode (User Mode) 是非特权模式 (Unprivileged Mode), 只能进行基本计算. 是应用程序运行的用户态 CPU 执行模式. 不能执行特权指令, 不能直接影响其他应用程序的执行.

S-Mode (Supervisor Mode) 是特权模式 (Privileged Mode), 能限制 APP 的执行与内存访问, 是操作系统运行的内核态 CPU 执行模式, 能执行 S-Mode 特权指令, 能直接影响其他应用程序执行.

H-Mode (Hypervisor Mode) 也是特权模式 (Privileged Mode), 能限制 OS 访问的内存空间, 是 VMM (Virtual Machine Monitor) 运行的 Hypervisor Mode CPU 执行模式, 能执行 H-Mode 特权指令, 能直接影响 OS 执行.

M-mode (Machine Mode) 也是特权模式 (Privileged Mode), 可以控制物理内存, 直接关机等, 是 Bootloader/BIOS 运行的 Machine Mode CPU 执行模式, 能执行 M-Mode 特权指令, 直接影响上述所有其他软件的运行, 可以访问所有 CSR (Control and State Register), 能处理最底层的如中断, 异常, 时钟, 物理内存保护等.

特权级是为不同软件栈部分提供的一种保护机制, 在任何时候, 一个 RISC-V 硬件线程 (hart, 即 CPU core) 是运行在某个特权级上的 (注意是某个, 意思是不同的特权级有不同的 CSR), 这个权限级由 CSR 配置.

当处理器执行当前特权模式不允许的操作时将产生一个异常, 这些异常通常会产生 trap 导致下层执行环境接管控制权.

特权级的跨越可以通过几条特殊指令来实现, 比如 ecall, sret, mret.

CSR 寄存器

寄存器分两类:

  • 通用寄存器 x0~x31 (有编程用名方便记忆和使用, 比如 x10 对应 a0, argument 0, 也就是第一个参数). 可以用一般指令访问
  • 控制状态寄存器 (CSR, Control and Status Registers), 需要通过控制状态寄存器指令 (单独的指令) 来访问, 可以有 4096 个 CSR

运行在用户态的应用程序不能访问大部分的 CSR 寄存器 (个别只读 CSR 可以访问, 比如获取时钟信息或其他通用信息). 而运行在内核态的操作系统可以通过访问 CSR 寄存器来控制计算机.

常见的通过设置 CSR 实现的隔离有:

  • 权利隔离: 防止应用访问系统管控相关寄存器, 用地址空间配置寄存器 mstatus/sstatus CSR
  • 时间隔离: 防止应用长期使用 100% 的 CPU, 用中断配置寄存器 sstatus/stvec CSR
  • 数据隔离: 防止应用破坏窃取数据, 用地址空间相关寄存器 sstatus/satp/stvec CSR

M-Mode 编程

M-Mode 是 RISC-V 中 hart 的最高权限模式, 对计算机系统的底层功能有完全的使用权.

M-Mode 最重要的特性是拦截和处理异常和中断:

  • 异常是同步的: 执行期间产生, 访问无效的寄存器地址, 或执行了无效操作码的指令
  • 中断是异步的: 指令流异步的外部事件, 中断, 如时钟中断

RISC-V 要求实现精确异常: 保证异常之前的所有指令都完整执行, 后续指令都没有开始执行.

硬件会负责设置这些 CSR 寄存器, 而软件需要把它们读出来.

中断时异步发生的, 通常是来自处理器外部的 I/O 设备的信号的结果. 而 Timer 可以稳定产生中断, 可以:

  • 防止应用程序死占着 CPU 不妨, 让 Kernel 能得到执行权
  • 由高特权模式下的软件获得 CPU 控制权
  • 也可由高特权模式下的软件授权低特权模式软件处理中断

目前 RISC-V 的设计中, 可以 disable 掉中断, 但是不能 disable 异常.

通常处理器与外设之间还有一个中间结构, 比如 RISC-V 中的 PLIC (Platform Level Interupt Controller), 负责识别是哪一个外设产生的中断.

scause 的最高位, 1 表示中断, 0 表示异常.

当中断/异常发生时, 被打断的那条指令的 PC 就会保存在 mepc 内, 然后将 PC 设置为 mtvec.

  • 对于异常, mepc 指向导致异常的指令
  • 对于中断, mepc 指向中断处理后应该恢复执行的位置

在产生一个中断之后, 通常会把 mstatus[MIE位] 置零以禁用中断 (避免中断没处理完又产生了下一个中断), 并把先前的 MIE 值保存在 MPIE 中.

还需要注意, 发生异常/中断时, 处理器控制权不会移交给权限更低的模式.

中断/异常的响应

当接收到中断时, 硬件需要设置中断标记, 然后依据中断向量调用相应中断服务.

软件需要:

  • 保存当前处理状态
  • 执行中断程序
  • 清除中断标记
  • 恢复之前的保存状态

中断控制和状态寄存器

这里详细说明中断发生时, 相关 CSR 是如何工作的.

mstatus (Machine Status) 保存全局中断以及其他状态. 涉及中断的几个 bits:

  • mie (Machine Interupt Enable) 位, 控制中断是否启用
  • mpie (Machine previous Interupt Enable) 位, 记录中断发生之前 mie 的值
  • spp (Supervisor Previous Privilege), 记录变化之前的特权级别是 S-Mode 还是 U-Mode
  • mpp (Machine Previous Privilege), 记录变化之前的特权级别是 M-Mode 还是 U-Mode

mcause (Machine cause), 最高一位用来指示是 interrupt 还是 expect (异常). 其他位用来指示 interrupt/exception 事件的编号.

M-Mode 下中断的硬件响应流程如下:

  • 对于同步异常, mepc (Machine Exception Program Count) 指向导致异常的指令; 对于中断, mepc 指向中断处理后应该恢复执行的位置
  • 将 pc 设置为 mtvec (Machine Trap Vector) 的值
  • 根据 interrupt/exception 来源设置 mcause, 并将 mtval (Machine Trap Value) 设置为出错的地址或者特定异常的信息字
  • 先将 mstatus[mie] 值保存在 mpie 中, 然后将 mstatus[mie] 位置零以禁用中断 (还有 sie 和 spie 要考虑)
  • 将发生异常之前的权限模式保存到 mstatus[mpp], 然后更改特权模式为 M
  • 跳转到 pc 指向的位置开始执行

需要注意, 上面 trap 的过程是一个原子操作, 在一个时钟周期内同时完成, 不存在顺序.

S-Mode 编程

S-Mode 需要避免 U-Mode 的 APP 执行越权指令, 非法地址或长期占用处理器. 还要让 U-Mode 的 APP 能够得到 S-Mode 的 OS 的服务.

同样要注意此时的:

  • 中断/异常机制
  • 异常/中断的硬件处理
  • 异常/中断的软件处理
  • 虚存机制

MMU 负责地址转换, TLB 是页表下的一个 cache.

关键指令

这里要有一个关键的认知, ecall 和 sret 这类指令会触发异常, 从而能够捕获. 在 U-Mode 执行 ecall 会触发名为 “Environment call from U-mode” 的异常. 在 S-Mode 执行会触发名为 “Environment call from S-mode” 的异常. 同理 M-Mode 会触发 “Environment call from M-mode”.

会用到 fence.i 指令, 用于清理 i-cache.

CPU 对物理内存所做的缓存又分成 d-cache 和 i-cache, OS 将修改会被 CPU 取址的内存区域, 这会使得 i-cache 中含有与内存中不一致的内容. OS 在这里必须使用 fence.i 指令手动清空 i-cache, 让里面所有的内容全部失效, 才能够保证 CPU 访问内存数据和代码的正确性.

特权级切换

这里相关的 CSR 有:

  • sstatus, spp 等字段给出 Trap 发生之前 CPU 的特权级 (S/U) 等
  • sepc, 记录 Trap 发生之前执行的最后一条指令的地址
  • scause, 描述 Trap 的原因
  • stval, 给出 Trap 附加信息
  • stvec, 控制 Trap 处理代码的入口地址

执行 ecall 时, 硬件会完成下面操作:

  • sstatus 的 spp 字段会被修改为 CPU 当前的特权级 (U/S)
  • sepc 会被修改为 Trap 处理完成后默认会执行的下一条指令的地址
  • scause/stval 分别会被修改成这次 Trap 的原因以及相关的附加信息
  • CPU 将当前特权级设为 S, 将 pc 设置为 stvec 所设置的 Trap 处理入口地址

当 CPU 完成 Trap 处理准备返回的时候, 需要通过一条 S 特权级的特权指令 sret 来完成, 这一条指令具体完成以下功能:

  • CPU 会将当前的特权级按照 sstatus 的 spp 字段设置为 U 或者 S
  • CPU 会将 pc 设置为 sepc 寄存器指向的那条指令, 然后跳转执行

可以看到, 运行 ecall 时, 硬件并不会自动保存 x0-x31 这些通用寄存器, 因此需要自己手动保存, 这里就需要用到栈. 需要专门为内核设置一个内核栈.

用户栈和内核栈

之所以还要建立一个内核栈, 就在于内核的设计是完全不信任用户程序, 这里也不会相信用户为内核建立了一个可用的用户栈. 建立内核栈能保证所有控制逻辑内核自己知道 (都是基于安全的考虑).

第四讲 多道程序与分时多任务

相关背景与基本概念

操作系统的被广泛使用是从大型机向小型机 (minicomputer) 过渡的时期开始的.

多道程序 (Multiprogramming):

  • 在内存中存在多个可执行程序
  • 各个可执行程序共享处理器

工作 (Job):

  • 应用的一次执行过程

Job 和 Multiprogramming 都是 IBM 用于多道程序设计的概念.

协作式调度 (Cooperative scheduling):

  • 可执行程序主动放弃处理器的使用
  • 操作系统不会打断正在执行的程序
  • 操作系统选择下一个执行程序使用处理器

后续的操作系统都会支持抢占. 小型机 (minicomputer) 的普及和广泛使用推动了分时多任务的需求, 形成了支持多用户的分时操作系统.

分时多任务 (Time sharing multitask), 从用户的视角看:

  • Task 表示应用的一次执行过程
  • 在内存中存在多个可执行程序
  • 各个可执行程序分时共享处理器
  • 操作系统按时间片来给各个可执行程序分配 CPU 使用时间

从操作系统角度看:

  • Task 是一个具有一定独立功能的程序在一个数据集合上的一次动态执行过程 (可以把 task 认为是 process 的一个前身, process 管控了更多资源)
  • 应用执行过程中的一个时间片段上的执行片段或空闲片段称为 “计算任务片” (占了 CPU) 或 “空闲任务片” (没占 CPU)
  • 从一个应用的任务切换到另外一个应用的任务称为任务切换

抢占式调度 (Preemptive scheduling):

  • 可执行程序被动地放弃处理器使用
  • 可执行程序按时间片轮流使用处理器, 是一种 “暂停-继续” 组合的执行过程
  • 基于时钟硬件中断机制, 操作系统可随时打断正在执行的程序
  • 操作系统选择下一个执行程序使用处理器

任务的特点:

  • 动态性: 开始执行 -> 暂停 -> 继续 -> 结束执行的过程
  • 并发性: 一段时间内多个任务在执行 (注意不是同一个时间, 同一个时间就是并行了)
  • 有限度的独立性: 任务之间不用感知对方的存在

目前还没具备的更强大的特点: 隔离更彻底, 任务间的协同, 任务创建任务等…

当这些都有了, 则称为进程.

Task (加载到内存中的代码) 和程序 (磁盘上的代码) 的关系如下:

Task 是操作系统处于执行状态时对程序的抽象:

  • 程序 = 文件 (静态的可执行文件)
  • Task = 执行中的程序 = 程序 + 执行状态 (加载到内存中, 对 CPU 寄存器的修改)

任务执行需要的资源:

  • 内存: 保存代码和数据
  • CPU: 执行指令

任务是动态的, 程序是静态的:

  • 程序是有序代码的集合
  • 任务是程序的执行

任务是暂时的, 程序是永久的:

  • 任务是一个状态变化的过程 (内存, CPU 寄存器)
  • 程序可长久保存 (磁盘)

任务与程序的组成不同:

  • 任务的组成包括程序, 数据和进程控制块

任务的组成

任务包含了运行程序的所有状态信息:

  • 任务执行的控制流: 代码内容与代码的执行位置 (代码段, CPU 从哪里取指令来运行)
  • 任务访问的数据: 被任务读写的内存 (堆, 栈, 数据段), 被任务读写的寄存器 (通用寄存器等)
  • 操作系统管理任务的相关数据 (任务上下文, 任务被中断打断的时刻, 或任务执行系统调用的时候, 需要保存对应的状态): 任务切换所需的通用寄存器; 任务切换所需的状态寄存器 (PC 等); 其他信息如任务的栈地址; 其他资源

操作系统管理任务

为了进行管理, 将这些状态存起来, 就设计了一个数据结构: 任务控制块 (TCB, Task Control Block). 之后操作系统才能进行有效的管理, 记录, 修改状态.

  • 操作系统管理控制进程运行所用的信息集合
  • 操作系统用 TCB 来描述进程的基本情况以及运行变化的过程
  • TCB 是进程存在的唯一标志
  • 每个任务都在操作系统中有一个对应的 TCB

任务生命周期

到这里的时候突然又回想起 sret 和 ecall 在两个态之间转换的流程, 再整理一遍.

计算机上电启动后, 操作系统先在内核态:

  • 手动向内核栈压入一个上下文, 包括 sepc 指向加载到内存中的用户程序, sstatus 各标志等
  • 执行 sret, pc <- sepc, CPU 从内核态标记为用户态, 之后跳转执行
  • 用户态执行 ecall, 保存返回地址 sepc <- pc (当前 ecall 的地址); 保存特权级 sstatus.SPP <- U-mode; 保存中断使能位: sstatus.SPIE <- sstatus.SIE; 禁用中断 sstatus.SIE <- 0; 然后跳转到内核的某个位置 pc <- stvec (handler 就是内核的一部分); CPU 从用户态标记为内核态, 然后跳转执行

创建任务就是将其初始状态设置好. 之后任务就处于就绪状态, 操作系统可以运行它.

执行时操作系统需要从内核态切换到用户态来执行.

任务进入等待的原因可能是:

  • 自身, 自己交出 CPU, 比如 sleep, 等待 IO, 网络等
  • 外界, 操作系统抢占

唤醒等待可能是:

  • 自身, 等待时间结束, 自然醒
  • 外界, 外设产生中断来恢复

任务被抢占的原因: 通常都是用时钟中断产生中断, 然后把任务放回就绪状态.

任务退出的原因通常也是两种:

  • 自愿, 比如程序执行 exit
  • 被迫, 操作系统 kill 掉

最重要的三种状态就是: 就绪, 运行, 等待.

这些状态的切换涉及哪些系统调用呢:

  • 运行 -> 退出, 涉及 sys_exit
  • 运行 -> 就绪, 只涉及中断
  • 运行 -> 等待, 涉及 sys_sleep
  • 等

在任务的生命周期中, 进行任务切换的时机通常是:

  • 时间片用完
  • 等待结束
  • 退出
  • 等

并发任务栈的创建

对于多任务并发场景, 每个 task 都会有一个独立的用户栈和内核栈. 比如任务 A 在切换回用户态之后, 肯定会沿着调用链继续往下执行, 栈也会继续增长. 如果只有一个用户栈, 任务 B 的栈紧挨着任务 A 的, 就会直接被覆盖掉.

对于内核栈也是同理, 这里用一个例子来说明, 主要问题出在初始化上. 假设两个任务共享一个内核栈:

  • 对于两个任务的 task context, 初始化 sp 都指向这个栈的栈顶
  • 任务 A 先执行, 然后调用 yield 系统调用 trap 到内核态. 向内核栈压入 trap context 和 trap handler frame (函数栈帧)
  • 在 trap handler 内调用 __switch, 保存任务 A 的 task context, 并读取 Task B 的 task context 内容到寄存器中. 其中 sp 内核栈指针又重新指向了最初的栈顶
  • 如果在 Task B 执行过程中调用 yield 或者其他系统调用, 此时保存的 trap context 就会覆盖掉 Task A 的 Trap context 和 trap handler 信息

(__switch 做的仅仅是保存当前任务的上下文, 然后将下一个任务的上下文加载到寄存器中, 最后 ret 跳转到 ra 寄存器的所在位置)

因此需要让每个任务独立建立内核栈.

在编译原理里: 程序的控制流 (Flow of Control or Control Flow) 是指以一个程序的指令, 语句或基本块为单位的执行序列 (pc 寄存器的跳转).

在计算机组成原理里: 处理器的控制流是指处理器中程序计数器的控制转移序列.

从应用程序员的角度来看: 控制流是应用程序员编写的应用程序的执行序列, 这些序列是程序员预设好的. 统称为普通控制流 (CCF, Common Control Flow).

从操作系统 (除了操作系统自身外还要管很多应用) 程序员的角度来看控制流:

  • 应用程序在执行过程中, 如果发出系统调用请求, 或出现外设中断, CPU 异常等情况, 会出现前一条指令还在应用程序的代码段中, 后一条指令就跑到操作系统的代码段中去了
  • 这就是一种控制流的 “突变”, 即控制流脱离了其所在的执行环境, 并产生执行环境的切换. 我们把这种 “突变” 的控制流称为异常控制流 (ECF, Exceptional Control Flow).

站在硬件的角度来看普通控制流或异常控制流的具体执行过程, 我们会发现从控制流起始的某条指令开始, 指令可访问的所有物理资源的内容, 包括自带的所有通用寄存器, 特权级相关特殊寄存器, 以及指令访问内存等, 会随着指令的执行而逐渐发生变化.

把控制流在执行完某指令时的物理资源内容, 即确保下一时刻能继续正确执行控制流指令的物理/虚拟资源内容称为控制流的上下文 (Context), 也可称为控制流所在执行环境的状态.

对于当前实践的 OS, 没有虚拟资源, 而物理资源内容就是通用寄存器/CSR 寄存器.

如果一个控制流属于某个函数, 那么这个控制流的上下文简称为函数调用上下文.

一个控制流是属于操作系统中处理中断/异常/陷入的那段代码, 那么这个控制流的上下文简称为中断/异常/陷入上下文.

一个控制流是属于操作系统中任务 (进程) 执行相关的那段代码, 那么这个控制流的上下文简称为任务 (进程) 上下文.

RISC-V 架构中的嵌套中断问题

默认情况下, 当 Trap 进入某个特权级后, 在 Trap 处理的过程中同特权级的中断都会被屏蔽.

  • 当 Trap 发生时, sstatus.sie 会被保存在 sstatus.spie 字段中, 同时 sstatus.sie 置零, 这也就在 Trap 处理的过程中屏蔽了所有 S 特权级的中断
  • 当 Trap 处理完 sret 的时候, sstatus.sie 会被恢复到 sstatus.spie 内的值

也就是说, 如果不去手动设置 sstatus CSR, 在只考虑 S 特权级中断的情况下, 是不会出现嵌套中断 (Nested Interrupt) 的.

嵌套中断可以分为两部分: 在处理一个中断的过程中又被同特权级/高特权级中断所打断. 默认情况硬件会避免前一部分, 也可以通过手动设置来允许前一部分存在. 而后一部分无论如何设置都是无法避免的.

嵌套 Trap 则是指一个 Trap 过程中有再次发生 Trap, 嵌套中断算是嵌套 Trap 的一种.

地址空间

需要先理解计算机中与内存相关的主题, 比如存储的层次.

相关术语:

  • 物理地址 (Physical address): 用于内存芯片级的单位寻址, 与处理器和 CPU 连接的地址总线相对应
  • 逻辑地址 (Logical address): Intel 为了兼容, 将远古时代的段式内存管理方式保存了下来. 逻辑地址指的是机器语言指令中, 用来指定一个操作数或者是一条指令的地址 (函数, 变量对应的地址), 也是用户编程时使用的地址
  • 线性地址 (Linear address) 或也叫虚拟地址 (virtual address): 跟逻辑地址类似, 他也是一个不真实的地址, 如果逻辑地址是对应的硬件平台段式管理转换前地址的话, 那么线性地址则对应了硬件页式内存的转换前地址

对于 intel 而言, 逻辑地址, 经过段机制转换后会变成线性地址 (虚拟地址), 线性地址经过页机制转换后会变成物理地址.

RISCV 中没有段机制, 只有页机制, 它的逻辑地址对应的就是虚拟地址.

按速度排就是: 寄存器 > 高速缓存 > 内存 > IO.

每个进程的内存分配实际上是分散的.

操作系统中采用的内存管理方式有:

  • 重定位 (relocation)
  • 分段 (segmentation)
  • 分页 (paging)
  • 虚拟存储 (virtual memory/storage)

操作系统的内存管理高度依赖硬件:

  • 与计算机存储架构紧耦合
  • MMU (内存管理单元): 处理 CPU 存储访问请求的硬件

几个地址空间的定义:

  • 物理地址空间, 指物理内存的地址空间, 起始地址 0, 直到 MAX_phy (由具体内存硬件决定)
  • 虚拟地址空间, 指虚拟内存的地址空间, 起始地址 0, 直到 MAX_virt (由操作系统指定)
  • 逻辑地址空间, 指程序执行的地址空间, 起始地址 0, 知道 MAX_prog (编译器决定)

逻辑地址生成过程:

如果应用程序中用到了动态链接库, 而动态链接库就是需要进行 “重定位” 的程序.

地址的几个生成时机有:

  • 编译时: 假设起始地址已知, 如果起始地址改变, 必须重新编译 (这里的编译包括了链接等过程)
  • 加载时: 如编译时起始地址未知, 编译器需要生成可重定位的代码 (relocatable code). 加载时, 位置可不固定, 生成绝对 (虚拟) 地址
  • 执行时, 执行时代码不可修改, 需地址转换 (映射) 硬件支持 (重点看这部分)

对于地址生成过程:

  • CPU 中, ALU 负责计算, 需要逻辑地址的内存内容; MMU 和进行逻辑地址物理地址的转换; CPU 控制逻辑会给总线发送物理地址请求
  • 内存, 发送物理地址的内容给 CPU 或接收 CPU 数据到物理地址
  • 操作系统, 建立逻辑地址 LA (Logical Address) 和物理地址 PA (Physical Address) 的映射

比如 ALU 想进行内存读时, 会涉及的流程:

  • Vaddr 指 virtual address
  • Paddr 指 physical address
  • TLB 没命中就会查页表, 页表中包含虚拟地址和物理地址的映射. 找到就会放到 TLB 中缓存起来
  • 如果页表中不存在, 则会产生异常, 交给 OS 处理. 如果是不合理的地址, 操作系统需要将程序 kill 掉. 如果在磁盘中, 会加载到内存中重建页表

虚拟存储的作用, 一个是把程序可用的地址空间扩大. 虚拟内存可作为外存的缓存:

  • 常用的数据放在物理内存中
  • 不常用的数据放在外存
  • 对运行的程序而言, 直接用虚拟地址, 不用关注具体放在物理内存还是外存

另一个好处是, 为每个应用程序提供独立的地址空间, 这让程序的编写更简单了. 可以简化应用编译和加载运行:

  • 每个运行程序具有独立的地址空间, 而不管代码和数据实际存放在物理内存的何处
  • 简化编译的执行程序链接过程
  • 简化操作系统的执行程序加载过程
  • 简化共享: 动态链接库, 共享内存
  • 简化内存分配: 物理不连续, 虚拟连续

还有就是安全, 虚拟内存可以保护数据:

  • 独立的地址空间使得区分不同进程各自内存变得容易
  • 地址翻译机制可以进行可读/可写/可执行的检查
  • 地址翻译机制可以进行特权级检查

  • 连续内存分配
  • 非连续内存分配
    (这俩是另一类分配方法)

动态内存分配主要有两类:

  • 显式分配 (explicit allocation): 要求应用显式地释放任何已分配的块 (比如 malloc, free)
  • 隐式分配 (implicit allocation): 编译器/运行时库自动释放未使用的已分配的块 (只用申请不用释放, 比如 java, python, go 运行时释放, rust 由编译器决定释放)

在 app 开发的视角, 动态内存的申请方式是:

  • 栈由编译器管理
  • 堆的分配和释放有程序员管理

对于申请的大小:

  • 栈是由高地址向低地址生长的数据结构, 是一块连续的内存, 能从栈中获得的内存较小, 编译期间确定大小
  • 堆是从低地址向高地址生长的数据结构, 是一个不连续的存储空间, 内存获取比较灵活, 也较大 (分配连续空间堆内存的系统调用时 sbrk, 如果是不连续指定一块地址, 需要用到 mmap 系统调用)

sbrk 是 Set Break 的缩写, 意思是设置进程数据段 (heap) 末尾 (program break) 的位置.

brk/sbrk 一词最早出现在 Unix Version 7 (1979), 其中 break 就是指堆顶 (program break). 因此 sbrk(n) 的意思就是 increment/decrement the break by n bytes. Set 这里是调整的意思. 即 sbrk = "set (the) break (by increment)".

在传统 Unix/Linux 中有:

  • brk(addr) 直接把 program break 设为 addr
  • sbrk(inc) 在当前 break 基础上偏移 inc, 返回旧的 break 地址

如果 malloc 比 free 多, 会造成内存泄漏. 如果 malloc 比 free 少. 会造成二次删除, 破坏内存, 导致程序崩溃.

对于内存管理者视角:

  • 连续内存分配指: 给应用分配一块不小于指定大小的连续的内存区域
  • 内存碎片指: 不能被利用的空闲内存. 外部碎片指分配单元间未被使用的内存; 内部碎片指分配单元内部未被使用的内存

提高内存分配的效率, 需要考虑:

  • 空闲块组织: 如何记录空闲块
  • 放置: 如何选择合适的空闲块来分配
  • 分割: 如何处理没分配完的空闲块中的剩余部分
  • 合并: 如何处理一个刚刚被释放的块

(黄色的是空闲块)

  • 而且查找速度也很快, 是二分的速度 $O(log n)$

  • 需要的分区大小为 $2^{(U-1)} < s \le s^U$ 时, 把整个块分配出去:
    • 如 $s \le 2^{(i-1)}$, 将大小为 $2^i$ 的当前空闲分区划分成两个大小为 $2^{(i-1)}$ 空闲分区 (比如请求分配 4 个块, 当前有 8 个块, 因此把 8 个块拆为两个 4 个块)
    • 重新划分过程, 直到 $2^{(i-1)} < s < 2^i$, 把一个空闲分区分配出去

数据结构:

  • 空闲块按大小和起始地址组织成二维数组
  • 初始状态: 只有一个大小为 $2^U$ 的空闲块

分配过程:

  • 有小到大在空闲块中找最小可用块
  • 如空闲块过大, 对可用空闲块进行拆分 (拆为两份)

释放过程:

  • 把块放入空闲块数组
  • 合并满足条件的空闲块

合并条件:

  • 大小相同 $2^i$
  • 地址相邻
  • 低地址空闲块起始地址为 $2^{(i+1)}$ 的位数

非连续内存分配

内核通过页表能够把多个地址不连续的物理页转换为地址连续的多个虚拟页, 提供给应用程序和内核自身使用地址连续的虚拟内存块, 这样可以比较轻松解决内存分配的碎片问题.

非连续内存分配的缘起:

  • 创建运行的程序时需要分配让其正常运行所需的比较大的内存空间
  • 程序运行时会需要动态申请和释放比较大的内存空间:
    • 通常用用户库发出请求
    • 减少系统调用次数
    • 一次申请 $2^U$ MB 大小的内存 (比如 glibc 一次请求 64MB 的内存, 如果不够, 接着会申请 128MB)

设计目标是提高内存的利用效率和管理灵活性:

  • 允许一个程序使用非连续的物理地址空间
  • 允许共享代码与数据
  • 支持动态加载和动态链接

页表机制由硬件提供.

非连续分配需要解决的问题:

  • 如何实现虚拟地址和物理地址的转换
    • 软件实现 (灵活, 开销大)
    • 硬件实现 (够用, 开销小)
  • 非连续分配的硬件辅助机制
    • 如何选择非连续分配中的内存块大小: 段式存储管理 (segmentation); 页式存储管理 (paging)

页式存储管理:

  • 页帧 (也叫帧, 物理页面, Frame, Page Frame), 把物理地址空间划分为大小相同 ($2^n$) 的基本分配单元
  • 页面 (也叫页, 逻辑页面, Page), 把逻辑地址空间也划分为相同大小的基本分配单位. 帧和页的基本单位大小是相同的
  • 页面到页帧, 逻辑地址到物理地址的转换. 需要硬件机制: 页表/MMU/TLB

  • 页表大小的容量问题: 页表可能非常大

  2. VPN[2] $\rightarrow$ L2 表的索引 $\rightarrow$ 得到 L1 表的地址

地址空间

从应用角度理解地址空间, 是一系列有关联但不一定连续的逻辑段. 这种关联一般是指这些逻辑段组成的虚拟/物理内存空间与一个运行的程序 (目前把一个运行的程序称为任务, 后续会称为进程) 绑定. 运行的程序对代码和数据的直接访问范围限制在它关联的地址空间之内.

具体来说:

  • 应用地址空间是编译器给应用生成的地址空间, 内核通过页表来约束应用地址空间, 应用不能访问它之外的地址空间
  • 内核地址空间是编译器给内核生成的地址空间, 内核通过页表调整应用/内核地址空间, 并管理整个物理内存

应用程序编译出会得到 .elf 文件, 里面有对各个 segment 很详细的描述, 包括位置信息, 因此内核能知道.

操作系统很多时候就是完成编译器无法完成的事.

跳板页

所有的应用与内核的跳板 Trampoline 页的虚拟地址是相同的 (都在高地址处), 且映射到同一物理页. 放置的是 trap.S 中的执行代码.

基于跳板页的平滑过渡主要包括:

  • 特权级过渡: 产生异常/中断时, CPU 会跳到跳板页的 _all_traps 入口
  • 地址空间过渡: 并在切换页表后, 可平滑地继续执行内核代码

跳板页的 __all_traps 汇编函数会保存相关寄存器到 trap context. 有:

  • Reg x[0..31]
  • CSR sstatus
  • CSR sepc
  • 内核页表的起始物理地址
  • app 的内核栈栈顶的虚拟地址
  • trap handler 入口点的虚拟地址

_restore 汇编函数会从 trap context 中恢复相关寄存器.

回顾之前没有页机制的 OS, trap context 保存在内核栈顶, sscratch 寄存器保存应用的内核栈.

  • 只通过 sscratch 寄存器中转用户/内核的栈指针
  • 当一个应用 Trap 到内核时, sscratch 已指向该应用的内核栈栈顶, 我们用一条指令即可从用户栈切换到内核栈, 然后直接将 Trap 上下文压入内核栈栈顶

由于有了页表的隔离, 用户程序无法直接访问内核地址空间, 因此要先进行地址的切换. 此时单用一个寄存器 sscratch 无法中转栈指针和页表基址两个内容.

这里直接把 trap context 放在了 APP 的虚拟空间里, 而不是 APP 对应的内核栈中. 此时就不需要先切换地址空间.

sscratch 内一开始存的是一个高地址, 用来存放 trap context.

  • sscratch 和 sp 内容交换, 之后 sscratch 存用户栈指针, sp 是高地址
  • 保存用户态寄存器, 以及之前说的其他内容到 trap context 中
  • 从 trap context 中读出内核页表基址, app 的内核栈栈顶指针, trap handler 的入口地址
  • 切换页表并跳转

这里需要注意, trap context 中并没有保存用户的页表位置. 这个是保存在 MemorySet 中的, 返回时会取出.

不需要存在 trap context 里的原因一个是用户页表地址在整个任务生命周期不变. 存 TaskControlBlock -> MemorySet -> token() 里面就行, 没必要每次 trap 都读一遍再写回去.

内核程序设计

内核需要建立, 感知虚拟/物理地址. 在内核/应用虚拟地址空间之间穿越.

内核要先给自己建立页表. 应用的页表体现的仅仅是 CPU “能看到” 的应用地址空间.

页表机制要能够管理物理内存, 建立内核/应用页表, 并使能页机制.

可用的物理内存 (RAM) 的大小仅设置为 8MB, 其中:

  • 物理内存起始地址: 0x80000000
  • 可用物理内存起始地址是: os/src/linker.ld 中的 ekernel 地址 (内核之后的才是其他应用可用的)
  • 物理内存结束地址: 0x80800000

此时的物理内存中包括:

  • 应用/内核的数据/代码/栈/堆
  • 空闲的空间

特别是各种管理类数据:

  • 任务控制块: Memory Set (应用/内核的多级页表等); 应用核心栈; 应用的 TrapContext 页

管理物理内存的一些做法 (以页为单位):

  • 物理内存上已经有一部分用于防止内核的代码和数据
  • 需要将剩下的空闲内存以单个物理页帧为单位管理起来
    • 当需要存应用数据或扩展应用的多级页表时分配空闲的物理页帧
    • 在应用出错或退出的时候回收应用占的所有物理页帧
  • 采用连续内存的动态分配策略
  • 分配/回收物理页帧的接口: 比如提供 alloc 和 dealloc 函数接口

建立内核/应用页表时需要注意:

  • SV39 多级页表是以页大小的节点为单位进行管理的. 每个节点恰好存储在一个物理页帧中, 它的位置可以用一个物理页号来表示.
  • 需要知道页表起始物理地址. satp 寄存器包含页表起始处的 PPN (PPN 和 offset 就能定位具体物理地址了)
  • 页表内容是虚拟地址和物理地址的映射关系, 有两种策略
    • 恒等映射 Identical Mapping (物理地址和虚拟地址一致)
    • 随机映射 Framed Mapping (地址间没有一种具体的关系)

建立过程, 每一个应用都会有自已一整套的页表 (比如 3 级), 先分配一个物理页帧, 用来放一级页表, 然后让 satp 指向它. 接着根据虚拟地址创建后面的表.

不同页表的基地址会放在应用的 trap context 中.

应用的逻辑段

应用的页表代表现实情况下的应用地址空间. 而应用的逻辑段代表了理想情况下的应用地址空间.

实现 SV39 多级页表机制

默认情况下 MMU 未被使能, 此时无论 CPU 处于哪个特权级, 访问内存的地址都会被直接视为是物理地址. 可以通过修改 S 特权级的 satp CSR 来启用分页模式, 此后 S 和 U 特权级的内存访问地址都会被视为虚拟地址, 经过 MMU 的地址转换能获得对应物理地址, 再通过它来访问物理内存.

ceil 为什么是 PAGE_SIZE - 1

PAGE_SIZE - 1 主要是处理当前已经对齐的情况, 比如 PAGE_SIZE = 4096, 而地址为 0x1000 (刚好是 4096), 此时 ceil 的语义该是不需要额外对齐, 不需要进位, 因为此时已经对齐了. 如果 ceil 实现是 + PAGE_SIZE, 那么 PhysPageNum 就会递增 1, (4096 + 4096) / 4096 = 2; 而实现如果是 + PAGE_SIZE - 1, 就恰好不会变, (4096 + 4096 - 1) / 4096 = 1.

MemorySet 的设计

MemorySet, 地址空间, 核心就是包含一个 PageTable 和一组 MapArea, 而 MapArea 中所涉及的所有 VirtPageNum, 都会由 PageTable 来管理.

这种设计的好处是:

  • PageTable 的生命周期与 MapSet 一致, 因此 PageTable 内部的 frames 的生命周期也与 MapSet 一致
  • areas 的生命周期与 MapSet 一致, areas 内部的 MapArea 的生命周期也与 MapSet 一致

内核地址空间

在分页开启之前, 内核和应用代码访存地址都会被直接视为物理地址, 而开启之后, 它们都需要通过 MMU 的地址转换变成物理地址, 再访问内存. 地址空间抽象的重要意义在于隔离 (Isolation), 每当我们在执行每个应用的代码的时候, 内核需要控制 MMU 使用这个应用自己的地址空间进行多级页表转换, 其得到的物理地址只能是在自己页表内有映射的部分. 别的物理地址没法访问到 (比如一个物理地址, 一个应用已经分配过了, 那么另一个应用的 PageTable 中一定不会记录该地址了, 也就无法被访问到).

假设一个应用在使用内核栈时, 函数调用层数过多或发生死递归, 就会导致栈溢出, 访问栈外的内容. 假如两个用户栈是挨在一起的, 内核不会知道栈超出了, 还会接着用错误的数据继续跑. 因为挨着的那个栈对应的虚拟页能找到物理页.

sfence.vma 的作用

在不使用多级页表时, 即线性表, 会占用大量内存, 但是只需要一次查找, 查找速度快. 使用多级页表时, 最快也需要三次访存. 为了解决性能问题, 一种常见的做法是在 CPU 中利用部分硬件资源额外加入一个快表 (TLB, Translation Lookaside Buffer), 它维护了部分虚拟页号到页表项的键值对. 当 MMU 进行地址转换时, 首先会从 TLB 中看看是否匹配, 如果匹配的话直接取出页表项完成地址转换而无需访存. 否则会再去查页表并将键值对保存在 TLB 中.

首先是编译, 对于用户程序, 由于有了虚拟地址空间, 因此链接脚本可以设置 BASE_ADDRESS = 0x0 了, 然后挨个放置程序里的各个段. 每个应用程序都会得到一个 elf 文件.

第六讲 地址空间-虚拟存储管理

基本概念

虚拟存储的需求来自程序规模的增长速度远远大于存储器容量的增长速度:

比如 50GB 的游戏是没法直接塞入内存的.

因此需要操作系统来建立一个理想中的存储器, 容量更大, 速度更快, 价格更便宜的非易失性存储器.

基本思路是, 内存不够, 外存来弥补. 按照历史发展的技术演变为:

  • 函数覆盖 (overlay): 应用程序以函数/模块为单位手动换入换出内存. 问题在于编程困难, 需要程序员划分功能模块, 并确定模块间的覆盖关系. 增加了执行时间, 从外存装入内存
  • 程序交换 (swapping): 操作系统以程序为单位自动换入换出内存. 但粒度太粗, 效率不高. 交换时机是内存不够的时候. 交换区大小通常是内存大小两倍. 而且程序换出换入后没法回到原先的位置 (有虚拟地址时就没事)

  • 虚拟存储 (virtual storage): 操作系统以页为单位换入换出内存

虚拟存储 = 内存 + 外存.

思路是操作系统将不常用的部分内存暂时存到外存, 将处理器要访问的数据从外存装入内存.

这里涉及到局部性这个概念. 局部性 (locality) 是程序在执行过程中的一个较短时期, 所执行的指令地址和指令的操作数地址, 分别局限于一定区域.

  • 时间局部性: 一条指令的一次执行和下次执行, 一个数据的一次访问和下次访问都集中在一个较短时期内
  • 空间局部性: 当前指令和临近的几条指令, 当前访问的数据和邻近的几个数据都集中在一个较小的区域内
  • 分支局部性: 一条跳转指令的两次执行, 很可能跳到相同的内存位置

局部性的意义是: 如果大部分程序运行具有局部性特征, 虚拟存储技术是能够实现的, 而且可取得满意的效果.

虚拟存储的基本规则是:

  • 状态程序时, 只将当前指令执行需要的部分页面或段装入内存
  • 指令执行中需要的指令或数据不在内存 (称为缺页或缺段) 时: 处理器通知操作系统将相应的页面或段调入内存
  • 操作系统将内存中暂时不用的页面或段保存到外存

实现方式就是虚拟页式存储或虚拟段式存储.

虚拟存储的一些基本特征:

  • 不连续性, 虚实地址的映射不是连续的. 物理内存分配非连续, 虚拟地址空间使用非连续
  • 大用户空间, 提供给用户的虚拟内存可大于实际的物理内存
  • 部分交换, 虚拟存储只对部分虚拟地址空间进行调入和调出

虚拟存储的底层支持需要有:

  • 硬件 (MMU/TLB/PageTable), 页式或段式存储中的硬件地址转换机制, 硬件异常
  • 软件 (OS), 内存中建立页表或段表. 管理内存和外存间页面或段的换入和换出

增加虚拟存储需要在页式存储管理的基础上, 增加请求调页和页面置换, 基本思路是:

  • 当用户程序要装载到内存时, 只装入部分页面, 就启动程序运行
  • 用户程序在运行中发现有需要的代码或数据不在内存时, 则向系统发出缺页异常请求
  • 操作系统在处理缺页异常时, 将外存中相应的页面调入内存, 使得用户程序能继续运行
  • 当内存快用完时, 操作系统把部分页从内存调出到外存

进程管理

主要涉及几个方面:

  • 进程切换
  • 进程创建/复制
  • 程序加载并执行
  • 进程等待与退出

进程的切换与任务切换类似, 需要暂停当前运行进程, 从运行状态变成其他状态. 接着调度另一个进程从就绪状态变为运行状态.

进程切换需要满足, 切换前保存进程上下文; 切换后恢复进程上下文. 进程上下文是从 Trap 上下文, Task 上下文, 含地址空间的上下文逐渐递进过来的.

进程生命周期的信息包括:

  • 寄存器 (PC, SP, …), 目的是便于从内核态回到用户态时能正常运行
  • CPU 状态
  • 内存地址空间, 会发生地址空间的切换

Unix 的进程创建/复制相关的系统调用是 fork/exec:

  • fork() 把一个进程完全复制一份, 此时就有两个进程 parent(old PID), child(new PID)
  • exec() 用新的程序来重写 (覆盖) 当前进程 (此时 PID 没有改变)

exec 这个系统调用还是很重要的, 不然只能复制自己, 而不能运行新的程序.

fork() 会创建一个复制了父进程大量内容的子进程:

  • 复制父进程的所有变量和内存 (复制了地址空间)
  • 复制父进程的所有 CPU 寄存器 (有一个寄存器例外)

fork() 执行过程对于子进程而言, 是对父进程地址空间的一次复制过程.

fork() 由于会对子进程分配内存, 复制父进程的内存和 CPU 寄存器到子进程里, 所有开销比较昂贵. 并且由于大部分场景下, 调用 fork() 之后都会调用 exec(), 因此之前的复制是无效的, 因为马上会被覆盖掉.

后续出现了 vfork() (virtual fork) 这个系统调用, 其在创建进程时, 不再立即创建一个相同的内存映像, 而是使用 Copy on Write 技术, 同样期望子进程立即调用 exec():

  • 注意看图左边, Parent page table 和 Child page table 的同一个 Entry 都指向同一个物理页帧, 因为此时没有分配新的内存
  • 右边是在遇到有对内存进行修改的操作时, 才给子进程分配新的物理内存

这里最终还是会分配内存 (毕竟两个进程运行状态不同, 寄存器啥的肯定不一样, 发生 trap 就会进行写操作), 但是避免了先完整复制父进程, 再用 exec 覆盖的这层开销.

Copy on Write 技术会先将父进程地址空间对应的物理页设置为只读, 如果两个进程最终都没有进行写操作, 那么这个共享就是安全的没问题. 如果进行写或执行操作, 就会触发异常, 此时再给子进程分配新的内存即可. 这里要区分一下, 是原本就是只读的页面被写了触发的异常, 还是说这里 Copy on Write 导致的. 这个就需要借助 MapArea 里面设置的权限, 这个结构体中说明了这段虚拟页是可写的, 此时还触发了异常, 就说明了是 Copy on Write.

对于进程的等待与退出, 如父进程等待子进程, 会用到 wait() 系统调用:

  • 子进程结束时通过 exit() 向父进程返回一个值; 父进程通过 wait() 接受并处理返回值
  • wait() 系统调用在有子进程存活时, 会让父进程进入等待状态, 等待子进程的返回结果. 当某子进程调用 exit() 时, 唤醒父进程, 将 exit() 返回值作为父进程中 wait 的返回值

如果子进程执行了 sys_exit() 退出, 但是没有被父进程用 sys_wait 系统调用回收 (回收内核中的 TCB), 此时称为僵尸进程, 等待僵尸进程时, wait() 会立即返回一个值 (也就是说, 僵尸进程只是子进程回收前的一个状态).

如果父进程比子进程先退出, 则形成了孤儿进程, 孤儿进程会由 root 进程负责等待并回收 (将父进程指向 root).

进程结束时需要调用 exit() 来完成进程资源的回收, 该系统调用的功能有:

  • 将调用参数作为进程的 “结果”
  • 关闭所有打开的文件等占用资源
  • 释放内存
  • 释放大部分进程相关的内核数据结构
  • 保留结果的值, 检查是否父进程存活, 如果没有存活, 设置父进程为 root 进程
  • 进入僵尸状态 (zombie/defunct), 等待父进程回收

其他与进程管理相关的系统调用还有:

  • 优先级控制: nice() 能指定进程的初始优先级. Unix 中进程优先级会随执行时间而衰减
  • 进程调试支持: ptrace() 运行一个进程控制另一个进程的执行, 可以设置断点和查看寄存器等
  • 定时: sleep() 可以让进程在定时器的等待队列中等待执行
  • 等

单处理器调度

单处理器调度就是假设计算机只有一个处理器时的调度问题.

进行处理器调度主要是为了更充分利用 CPU, 让 CPU 不要闲下来. 这里涉及到进程的切换, 即 CPU 资源的当前占用者切换. 需要保存当前进程在 PCB 中的执行上下文 (CPU 状态), 并且恢复下一个进程的执行上下文.

如何选择下一个进程就涉及到处理器调度: 从就绪队列中挑选下一个占用 CPU 运行的进程, 从多个可用 CPU 中挑选就绪进程可使用的 CPU 资源.

还需要考虑调度时机, 在进程/线程的生命周期中的什么时候进行调度. 调度也分两类: 非抢占系统, 当前进程主动放弃 CPU; 可抢占系统, 通过中断请求进行进程切换.

比较调度算法好坏的指标通常有:

  • CPU 使用率, CPU 处于忙状态的时间百分比
  • 吞吐量, 单位时间内完成的进程数量
  • 周转时间, 进程从初始化到结束 (包括等待) 的总时间
  • 就绪等待时间, 就绪进程在就绪队列中的总时间
  • 响应时间, 从提交请求到产生响应所花费的总时间
  • 公平, 进程占用相同的资源, CPU 时间等. 保证每个进程占用相同的 CPU 时间, 保证每个进程的就绪等待时间相同. 公平通常会增加平均响应时间

但很多时候与应用和场景挂钩, 比如有时需要低能耗, 就不需要 CPU 一直跑满. 有些指标也会有矛盾, 比如既要大吞吐量, 又要低延迟 (一般追求 balance).

常见调度算法有:

  • 先来先服务算法
  • 短作业优先算法
  • 最高响应比优先算法
  • 时间片轮转算法
  • 多级反馈队列算法
  • 公平共享调度算法

先来先服务算法

先来先服务算法 (FCFS, First Come, First Served), 核心思想是: 依据进程进入就绪状态的先后顺序排列, 进程进入等待或结束状态时, 就绪队列中的下一个进程占用 CPU. 可以用周转时间作为其评价指标.

这其实就是批处理系统的调度方式. 在任务长度都比较短, 或长度差不多, 或者任务数少且长度非常长的时候可以考虑这个算法.

短作业优先算法

短作业优先算法 (Short Job First), 核心思想是选择就绪队列中执行时间最短的任务/进程来占用 CPU 从而进入运行状态. 就绪队列会按照预期的执行时间来排序.

还有一个问题, 如何确定一个任务的执行时间呢, 只有知道这个才能进行排序. 最简单的方式就是用户设定 (难以让计算机进行估计).

最短剩余时间算法

最短剩余时间算法 (Short Remaining Time, SRT), 上一种方法是不允许强制打断的, 而 SRT 支持抢占式调度, 即有新的进程就绪, 且新进程的服务时间小于当前进程的剩余时间, 则会转到新的进程执行.

最高响应比优先算法

最高响应比优先算法 (Highest Response Ratio Next, HRRN), 是对 FCFS 调度算法和 SJF 调度算法的一种综合平衡, 同时考虑每个作业的等待时间 (这里的等待是就绪队列中的等待时间) 和估计的运行时间. 在每次进行作业调度时, 先计算后被作业队列中每个作业的响应比, 从中选出响应比最高的作业投入运行.

响应比 R 的计算方法是 $R = \frac{w + s}{s}$:

  • w 是就绪等待时间 (waiting time)
  • s 是执行时间 (service time)

该方法能防止进程永久饥饿.

时间片轮转算法

前面的算法只考虑了 CPU 的执行时间, 但没有考虑 IO 时间, 因此难以满足实时交互的要求.

RR (Round Robin), 该算法以时间片 (分配处理器资源的基本时间单元) 为单位, 在时间片结束后, 按 FCFS 算法切换到下一个就绪进程, 每隔 (n-1) 个时间片一个进程就能执行一个时间片 q 的时间.

  • 时间片太大: 等待时间过长, 极限情况退化成 FCFS
  • 时间片太小: 反应迅速, 但产生大量上下文切换. 大量上下文切换开销影响到系统吞吐量

多级队列调度算法

RR 算法不太灵活. 之前的算法都没有考虑进程的优先级.

MQ (MultiQueue) 算法的思想是: 就绪队列被划分为多个独立的子队列, 比如前台进程 (交互) 子队列, 后台进程 (批处理) 子队列. 同一优先级的的进程属于某个队列, 且不能跨越队列.

每个队列拥有自己的调度策略, 比如前台进程 (考虑响应性, 通常优先级更高) RR, 后台进程 (不考虑响应性) 用大时间片的 RR/FCFS.

算法有两个运行规则:

  • 如果 A 的优先级 > B 的优先级, 那么运行 A (不运行 B)
  • 如果 A 的优先级 = B 的优先级, 轮转运行 A 和 B

这种算法的一个风险是, 由于优先保证高优先级的队列, 那么这种固定优先级的方式会导致低优先级的队列饥饿. 正确的考虑是, 在时间运行过长时, 应该降低优先级; 而时间运行过短的队列该提升优先级.

后面就出现了 MLFQ (Multi-Level Feedback Queue, 多级反馈队列), 在 1962 年由 MIT 教授 Corbato 首次提出, 应用于兼容时分共享系统 (CTSS-Compatible Time-Sharing System). 解决两方面问题:

  • 如何在不知道工作要运行多久的情况下, 优化周转时间
  • 如何降低响应时间, 给交互用户更好的交互体验

这里的重点就是 Feedback, 它会根据进程情况动态调整优先级.

其继承了 Multi Queue 的两个调度规则, 之外还有一些扩展, 基本的如下:

  • 工作进入系统时, 放在最高优先级 (最上层队列)
  • 如果进程在当前的时间片结束时没有运行完成, 则会降到下一个优先级
  • 如果工作在其时间片以内主动释放 CPU (比如 yield, sleep), 则优先级不变
  • 时间片大小随优先级级别增加而增加

下面是三个优先级队列的 MLFQ 调度示例: CPU 密集型进程首先进入最高优先级队列; 执行 1ms 时间片后, 调度器将进程的优先级减 1, 进入次高优先级队列; 执行 2ms 时间片后, 进入系统的最低优先级队列, 一直留在那里, 按 4ms 时间片执行.

MLFQ 算法的特征是:

  • CPU 密集型进程的优先级下降很快
  • I/O 密集型进程停留在高优先级

潜在的问题是:

  • CPU 密集型进程会饥饿
  • 恶意进程会想办法留在高优先级

一种提升优先级的方法是: 经过一段时间 $S$, 就将系统中所有工作重新加入最高优先级队列.

对于惩罚主动放弃 CPU 但不降低优先级的方式: 一旦工作用完了其在某一层的时间配额, 就降低其优先级.

公平共享调度算法

FSS (Fair Share Scheduling), 核心思想是控制用户对系统资源的访问:

  • 不同用户拥有多个进程
  • 按用户优先级分配资源
  • 保证不重要的用户无法垄断资源
  • 未使用的资源按比例分配

它能够应对的问题是, 如果一个用户拥有很多进程, 那么他的总执行时间肯定会更长.

实时管理与调度

主要针对嵌入式系统. 这里需要了解实时操作系统这个概念: 正确性依赖于其时间和功能两方面的操作系统.

实时操作系统的性能指标有:

  • 时间约束的及时性 (deadlines)
  • 速度和平均性能相对不重要

实时操作系统的特性:

  • 时间约束的可预测性

强调确定性, 必须在某个 deadline 之前完成, 不然会产生严重后果. 不要求速度要多么快, 只要在规定时间内完成就行.

实时操作系统分两类:

  • 强/硬实时操作系统: 要求在指定的时间内必须完成重要的任务
  • 软/弱实时操作系统: 重要进程有高优先级, 要求尽量但非必须完成

这里介绍两种任务.

实时任务, 只要在绝对截至时间之前完成就行, 比如一次计算, 一次文件读取, 一次信息传递等. 任务的属性包括完成任务所需要的资源, 定时参数等.

(任务执行时间在绝对截止时间内)

另一种是周期实时任务, 任务有规律地重复运行:

  • 周期 p (period) 为任务请求时间的间隔 ($0 < p$)
  • 执行时间 e (execution) 为最大执行时间 ($0 < e < p$)
  • 使用率为 $U = e/p$

通常只有 $\sum_{p_i} \frac{e_i}{p_i} \lt 1$ (没有把一个周期占满) 才是可调度的, 否则不可调度.

软时限和硬时限

软时限 (Soft deadline) 指:

  • 通常能满足任务时限
  • 如有时不能满足, 则降低要求
  • 尽力保证满足任务时限

硬时限 (Hard deadline) 指:

  • 错过任务时限会导致灾难性或非常严重的后果
  • 必须验证, 在最坏情况下能够满足时限

可调度性

可调度表示一个实时操作系统能够满足任务时限的要求, 这就需要能够确定实时任务的执行顺序.

执行顺序与任务优先级相关, 有两类调度方式:

  • 静态优先级调度, 任务执行过程中不会改变任务的优先级
  • 动态优先级调度, 任务执行过程中会改变任务的优先级

设计设备驱动程序的总体思路

在内核中添加设备驱动的大致开发过程如下. 需要先开发出在没有操作系统的裸机环境下具备基本功能的裸机设备驱动 crate, 然后在操作系统中通过一层封装来使用.

在了解了应用程序或操作系统中的其他子系统需要设备驱动程序完成哪些功能后, 完成下面基本操作:

  1. 设备扫描/发现
  2. 设备初始化
  3. 准备发给设备的命令
  4. 通知设备
  5. 接收设备通知
  6. 卸载设备驱动时回收设备驱动资源 (可选)

在进行裸机设备驱动开发前, 还需要了解对应设备的硬件规范. 这里主要有两类设备:

  • 实际的物理设备, UART (QEMU 模拟了这种 NS16550a UART 芯片规范)
  • 虚拟设备 (如各种 Virtio 设备)

然后还需要了解外设是如何与 CPU 连接的. 首先是 CPU 访问外设的方式, 在 RISC-V 环境中, 是 MMIO 映射方式, 即把外设相关的控制寄存器映射为某特定的内存区域, 然后 CPU 通过读写这些特殊区域来访问外设 (即 PIO 访问方式).

外设可以通过 DMA 来读写主机内存中的数据, 并可通过中断来通知 CPU. 外设并不直接连接 CPU, 此时就需要了解 RISC-V 中的平台级中断控制器 (Platform-Level Interrupt Controller, PLIC), 它管理并收集各种外设中断信息, 并传递给 CPU.

PLIC

PLIC (Platform-Level Interrupt Controller), 平台级中断控制器. 外设的中断线统一汇入 PLIC, PLIC 负责排队, 分发到 CPU.

没有 PLIC 时, 每个外设都需要一根线直连到 CPU, 这样引脚会不够用, 也无法进行优先级管理.

有 PLIC 之后:

每个外设通过一条中断线连接到 PLIC, 并有两个寄存器控制行为:

  • IE (Interrupt Enable, per-source), 控制是否启用中断
  • Priority, 设置优先级

I/O 设备

需要关注一个 I/O 设备能为软件提供的接口, 比如能够接收的命令, 能够完成的功能以及能产生的各种响应或错误等.

可以从数据传输的特点来给 I/O 设备进行分类. 早期的 UNIX 把 I/O 设备分为两类:

  • 块设备 (block device, 比如磁盘), 把信息存储在固定大小的块中, 每个块有独立的地址. 块的大小一般在 0.5KB 到 32KB 不等. 块设备的 I/O 传输以一个或多个完整的 (连续的) 块为单位
  • 字符设备 (character device, 比如串口, 键盘等), 以单个字符为单位发送或接收一个字符流. 字符设备不需要寻址, 只需访问 I/O 设备提供的相关接口即可获得/发出字符信息流

后来随着网络的普及, 又出现了一类设备: 网络设备. 网络面向报文而不是面向字符流或数据块, 还具有数据丢失等可靠性问题, 因此将网络设备映射为常见的文件比较困难. 为此 UNIX 的早期继承者 BSD (Berkeley Software Distribution) 提出了 socket 接口和对应操作, 形成了事实上的 TCP/IP 网络 API 标准.

再后来的 I/O 设备已经很难归类到上述的三种分类中了, 比如 GPU, 声卡等外设各自形成了独立的设备类型.

由于虚拟机与 OS 的 virtio 设备驱动程序间的通信是基于共享内存的异步访问方式来实现的, 因此对虚拟机中 virtio 设备的 I/O 操作能够转换为实际物理机上的物理外设的 I/O 操作.

简单来说, guest OS 只要实现了 virtio 设备的驱动, 就能够操作 virtio 设备, 跟进一步能转换为对物理机外设的操作.

virtio 协议最初是为虚拟机外设而设计的 IO 协议, 但是随着应用范围逐步扩展到物理机外设, virtio 协议正朝着更适合物理机使用的方向而演进.

下面是五种 IO 执行模型的详细描述.

Blocking IO:

  1. 用户进程发出 read 系统调用；
  2. 内核发现所需数据没在I/O缓冲区中，需要向磁盘驱动程序发出I/O操作，并让用户进程处于阻塞状态；
  3. 磁盘驱动程序把数据从磁盘传到I/O缓冲区后，通知内核（一般通过中断机制），内核会把数据从I/O缓冲区拷贝到用户进程的buffer中，并唤醒用户进程（即用户进程处于就绪态）；
  4. 内核从内核态返回到用户态的进程，此时 read 系统调用完成。

Non-blocking IO:

  1. 用户进程发出 read 系统调用；
  2. 内核发现所需数据没在I/O缓冲区中，需要向磁盘驱动程序发出I/O操作，并不会让用户进程处于阻塞状态，而是立刻返回一个error；
  3. 用户进程判断结果是一个error时，它就知道数据还没有准备好，于是它可以再次发送read操作（这一步操作可以重复多次）；
  4. 磁盘驱动程序把数据从磁盘传到I/O缓冲区后，通知内核（一般通过中断机制），内核在收到通知且再次收到了用户进程的system call后，会马上把数据从I/O缓冲区拷贝到用户进程的buffer中；
  5. 内核从内核态返回到用户态的进程，此时 read 系统调用完成。

IO multiplexing:
IO multiplexing对应的I/O系统调用是 select 和 epoll 等，也称这种IO方式为事件驱动IO(event driven IO)。 select 和 epoll 的优势在于，采用单进程方式就可以同时处理多个文件或网络连接的I/O操作。其基本工作机制就是通过 select 或 epoll 系统调用来不断的轮询用户进程关注的所有文件句柄或socket，当某个文件句柄或socket有数据到达了，select 或 epoll 系统调用就会返回到用户进程，用户进程再调用 read 系统调用，让内核将数据从内核的I/O缓冲区拷贝到用户进程的buffer中。

在多路复用IO模型中，对于用户进程关注的每一个文件句柄或socket，一般都设置成为non-blocking，只是用户进程是被 select 或 epoll 系统调用阻塞住了。select/epoll 的优势并不会导致单个文件或socket的I/O访问性能更好，而是在有很多个文件或socket的I/O访问情况下，其总体效率会高。

Signal driven IO: 当进程发出一个 read 系统调用时，会向内核注册一个信号处理函数，然后系统调用返回。进程不会被阻塞，而是继续执行。当内核中的IO数据就绪时，会发送一个信号给进程，进程便在信号处理函数中调用IO读取数据。此模型的特点是，采用了回调机制，这样开发和调试应用的难度加大。回调就是函数不会立即执行, 在进程接收到信号时才执行.

Asynchronous IO: 用户进程发起 async_read 异步系统调用之后，立刻就可以开始去做其它的事。而另一方面，从内核的角度看，当它收到一个 async_read 异步系统调用之后，首先它会立刻返回，所以不会对用户进程产生任何阻塞情况。然后，kernel会等待数据准备完成，然后将数据拷贝到用户内存，当这一切都完成之后，kernel会通知用户进程，告诉它read操作完成了.

平台级中断控制器

要让 OS 处理外设中断, 就需要对中断控制器进行初始化设置.

在 RISC-V 中, 与外设连接的 I/O 控制器的一个重要组成是平台级中断控制器 (Platform-Level Interrupt Controller, PLIC), 其一端汇聚了各种外设的中断信号, 另一端连接到 CPU 的外部中断引脚上. 当一个外部设备发出中断请求时, PLIC 会将其转发给 RISC-V CPU, CPU 会执行对应的中断处理程序来响应中断.

通过 RISC-V 的 mie (Machine Interrupt Enable) 寄存器中的 meie (Machine Enable Interrupt Enable) 位, 可以控制这个引脚是否接收外部中断信号.

通过 RISC-V 中 M Mode 的中断委托机制, 也可以在 RISC-V 的 S Mode 下, 通过 sie 寄存器中的 seie 位, 对中断信号是否接收进行控制.
